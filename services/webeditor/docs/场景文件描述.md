场景文件由一个 json 组成，其中具有若干 object，每个 object 带有若干 component 来实现不同功能。

对于需要渲染的场景，本服务强依赖 ObjectLibraryServer（OLS），需要从 OLS 获取模型元数据和模型文件等信息。

本文档以 `docs/ur5e_table_empty.json` 为参考样本，各节"本场景取值"给出的都是该文件里的真实数值（8 个物体，按 2026-10-14 从 OLS `GET /scene?id=1` 回写的样本核对；文件里的物体顺序是 `0、7、1、2、3、4、5、6`，id 7 是后加的顶部直射光）。字段语义与 `docs/Web前端需求规格v3.md` §2/§3 一致，落点代码在 `editor/src/world.ts`（解析）、`editor/src/renderer.ts`（渲染）、`editor/src/library.ts`（OLS 取数）。

## 1. 顶层结构

| 字段 | 类型 | 本场景取值 | 说明 |
|---|---|---|---|
| `scene_schema_version` | uint | `1` | 世界文件结构版本，浏览器只接受 `1`（`world.ts:SUPPORTED_SCHEMA_VERSION`） |
| `scene_version` | uint | `3` | 每次成功应用 `updateWorld`/`updateItem`/`addObject`/`removeObject` 后由浏览器自增 1（§3.9）。这四条是 `scene_version` 的**唯一**推进者。手动 Load Scene **不**本地自增，生效版本就是文件里写的这个 |
| `scene_sub_version` | uint | 缺省（本场景不写） | **可选**，缺失即合法、按 `0` 读（需求规格 §3.1，**Q109**）。只有 `setup` 阶段的浏览器本地内容增删（资产面板加物、层级面板本地删除）推进它，每次成功 +1；上面那四条 `scene_version` 路径每推进一次就把它归 0。写出规则与读取不对称：**只在 >0 时出现**，所以没人编辑过的现场逐字节回到原样，摘要不会为一次不存在的改动移动 |
| `scene_id` | uint | `1` | 场景 id（uint32）。 |
| `scene_name` | string | `"ur5e_table_empty"` | 展示用名称 |
| `objects` | Object[] | 7 项 | 见 §2 |

## 2. 物体（object）结构

| 字段 | 类型 | 说明 |
|---|---|---|
| `object_id_in_scene` | uint32 | 场景内唯一 id（§2.1）。负数/小数/字符串等非 uint32 → 该物体连同其整棵子树被拒绝，并在响应的 `rejected_objects` 中按 `index` 回报 |
| `object_name_in_scene` | string | 层级面板显示名；缺失时回退 `object_<id>` |
| `components` | Component[] | `[{ "component_type": …, "properties": … }]`，形态见 §4 |

id 与 OLS 的 `model_id`/`robot_id`/`scene_id` 是**三套互不相通的编号**（`model 2` 与 `robot 2` 是两个不同资产），不得混用（§2.4）。

## 3. 全局约定（所有组件共用）

- 长度单位 **米**（§2.7）。角度一律 **弧度**，唯一例外是 `Camera.fov` 为**度**（§2.6）。
- 四元数分量顺序一律 **xyzw**（§2.8），禁止按 wxyz 解释文件。
- 世界是 **Z-up**：渲染根 `simWorld` 自带 -π/2 的 Z-up 旋转，物体位姿不需要也不要自己再转一次；相机出图时再按 §4.4 的光学系约定（**局部 +Z 前、+Y 上、+X 左**，决议 Q74）转换。四元数为单位阵的相机因此看向世界 **正上方**，要拍桌面必须显式给安装姿态。
- `Transform` 的 `position/quaternion_xyzw/scale` 是**相对父物体**的局部位姿，不是世界位姿（§2.8）。
- **未知 `component_type` 不中断加载**：控制台告警后忽略，但原始字典仍保留在该物体的 `rawComponents` 里（§3.4、§3.8）。解析器自 2026-10-28 起识别**九类**组件，包括 `RobotAttachment`（见 §4.8）与新增的 `LocalAxes`（见 §4.9）；**但本文件这份样本场景里只出现前八类**——`LocalAxes` 还没有任何一个物体携带它，所以 §4 那张"本场景实际出现的组件"表里没有它的行。**第十类 `PhysicalProperties`（见 §4.10，决议 Q165）就走这条忽略路径**：解析器不把它当已识别组件建类型化视图，只按 §3.8 把整份字典原样留在 `rawComponents` 里备后续使用——读取端因此零改动，告警照旧、数据照旧不丢，`toJSON()` 也逐字节回吐（§3.8）。
- **同一类型重复出现**：只保留第一次出现的那个，其余告警忽略。
- **字段缺失按默认值回退，不报错**（§3.8 明确"不得假设字段一定存在"）。
- `properties` 里未声明的字段**不丢弃、不改名、不换算**，随原始字典整体保留在内存供后续功能取用（§3.8、决议 Q6）。

本场景实际出现的组件与识别情况：

| component_type | 出现的物体 | 解析器识别 |
|---|---|---|
| `Transform` | 0、1、2、3、4、5、6、7 | 是 |
| `MetadataRef` | 1、2、3、4、5、6 | 是 |
| `MeshRenderer` | 1、4、5、6 | 是 |
| `Semantic` | 1、2、3、4、5、6 | 是 |
| `Light` | 0、7 | 是 |
| `Camera` | 4、5 | 是 |
| `RobotDriver` | 2、3 | 是 |
| `RobotAttachment` | 3 | 是（覆盖 `Transform` 的位置与姿态，并把物体挂到 `parent_link` 节点上，见 §4.8） |

这张表数的是**本场景文件里实际写了的组件**。§4.9 的 `LocalAxes` 是 2026-10-28 新增的第九类，识别它、但这份样本里没有任何物体携带它，因此不在表内——它是文档级口径，不来自 `docs/ur5e_table_empty.json`（那份是用户维护的输入件，本文档不代它新增字段）。§4.10 的 `PhysicalProperties`（**Q165**）同理不在表内：这份样本一个物体都没带它，且它本就走 §3.4 的保留路径、不建类型化视图，"解析器识别"一栏对它不适用——前端只在摆放/替换物体时写它、读取时原样存（见 §4.10 与需求规格 §4.6.1）。

### 4.1 Transform

大部分物体都有的组件，用于描述该物体在世界中的位置和父子关系。

| 字段 | 类型 | 说明 |
|---|---|---|
| `position` | `[x,y,z]`（米） | 位置 |
| `quaternion_xyzw` | `[x,y,z,w]` | 旋转 |
| `scale` | `[sx,sy,sz]` | 缩放 |
| `parent` | uint \| null | 父物体id（如果没有则为null） |

- `parent` 指向的是**父物体的 `object_id_in_scene`**；`0xFFFFFFFF`（轨迹文件里的"场景根"哨兵值）一律映射为 `null`（§2.5）。
- 父物体不存在或层级成环 → 该子树整体拒绝（§3.6）。
- **完全没有 `Transform`** 的物体按单位位姿 + 场景根处理，并告警；物体仍会被创建（§3）。
- 这份位姿的语义是**相对 `parent` 的局部值**，不是世界值。**前端没有任何入口会改写它**（2026-10-20 需求规格 **Q114** 撤掉视口 gizmo，**Q79/Q80 就地废止**）：改 `position`/`quaternion_xyzw`/`scale` 的唯一通路是调用方那四条写入路径（需求规格 §3.9），父链语义不变。带 `RobotAttachment` 的物体也一样——**没有任何入口会去改写 `attachment.transform`**，**Q80** 那条"拖动挂载物体时同步写回挂载位姿"随 gizmo 一起作废。这份数据因此只有两个来源：文件里写的，与调用方随后改成的。

### 4.2 MetadataRef

指向 OLS 里的一份模型/机械臂资产，是"这个物体用什么几何去渲染"的唯一来源。取数流程见 §5。

| 字段 | 类型 | 说明 |
|---|---|---|
| `path` | string | 只接受形式为"$LIBRARY_SERVER/id"，表示元数据在OLS上，需要根据type字段向OLS请求元数据和模型数据。 |
| `type` | `"model"` \| `"robot"` | 用于向OLS请求时的类型 |

- `path` 缺失或为空字符串 → 告警 `MetadataRef without path, the object renders without a model`，该物体是空节点。
- **`type` 决定向 OLS 的哪一个 id 空间请求**：`"model"` → `GET {OLS}/model?id=`，`"robot"` → `GET {OLS}/robot?id=`，`path` 里的那个数字在所选空间内解释（`scene`/`model`/`robot` 是三套互不相通的编号，规格 §6.11）。`type` 为其它值（如 `"scene"`、`"urdf"`）或不是字符串 → **只告警不中断**（§3.4）：`MetadataRef type "scene" is neither "model" nor "robot", the path form decides`，该 `type` 被丢弃、改由 `path` 的形式决定，物体照常加载。
- `type` 缺失（或为 `null`/空串）时由 `path` 的形式决定：裸数字 `$LIBRARY_SERVER/<n>` 恒为 `model`；带路由的写法 `$LIBRARY_SERVER/robot?id=<n>`（含已替换的绝对 URL 与代理形式）为 `robot`；`scene?id=` 一律拒绝。两种写法都还能出现在已替换成 `http://<host:port>/model?id=<n>` 的 URL 里，此时路由名给出 id 空间，`type` 存在则以 `type` 为准。
- 无 `MetadataRef` 的物体（本场景的 `AmbientLight` 与 `TopDirectionalLight`，以及任何只带 Light/Camera 的物体）只创建空节点或对应组件的可视化，**不得生成占位立方体**（§3.7）。

### 4.3 MeshRenderer

| 字段 | 类型 | 说明 |
|---|---|---|
| `forceOverrideColor` | `#RRGGBB` 或 `#RRGGBBAA` | 有则用该纯色覆盖材质**并丢弃贴图**；后两位 `AA` 是透明度（写入材质的 `opacity`，小于 1 时同时置 `transparent`），只写 6 位时保持不透明；无则使用模型自带材质（§6.8） |

本场景取值：物体 1、4、5、6 都带 `MeshRenderer`，但 `properties` 是**空字典**——即不覆盖颜色，走模型自带材质。色值非法（无法解析）→ 报告 `forceOverrideColor "…" is not a #RRGGBB or #RRGGBBAA colour` 并保留原材质。判据是 **`#` 加 6 位或 8 位十六进制**（`#` 必须写，字母大小写不限），所以 `FF0000`、`#FF00`、`red`、`#FF0000FF00` 都算非法。

自 2026-10-14 的资产重导出起，纯色路线由**资产侧**承担：OLS `data/robots` 里 `1`（UR5e 臂身）、`2`（夹爪）、`4`、`9`、`13`、`14` 的 MTL 已不含 `map_Kd`，只留 `Kd`（`3` D435i 与 `11` 仍是带 UV 的真实贴图，属正常资产）；因此这份场景不写 `forceOverrideColor` 也能显示正确的固有色（决议 Q72、§6.8）。`forceOverrideColor` 本身仍是有效字段与调试手段，只是本样本没有用到。

物体 2（UR5eArm）与物体 3（夹爪）**没有** `MeshRenderer`：URDF link 声明的颜色只作用于**不含内嵌材质**的几何（STL），含材质的 DAE/OBJ+MTL/glTF 保留自身材质（§6.8、决议 Q15）。

### 4.5 Light

| 字段 | 类型 | 缺省值 | 说明 |
|---|---|---|---|
| `type` | `Ambient` \| `Directional` \| `Point` \| `Spot` | `Ambient` | 光照类型；**未知类型按 Ambient 回退并告警**。本样本出现过 `Ambient` 与 `Directional`，完整枚举仍是规格开放项 **O4**；`Spot` 是前端已实现的一档 |
| `intensity` | number | `1` | 非有限数值 → 按 `1` |
| `color` | CSS 色值 | `#FFFFFF` | 光色；缺失或不是可解析的 CSS 色值 → 白色 |

本场景取值：物体 0 `type: "Ambient"`、`intensity: 0.5`、`color: "#FFFFFF"`；物体 7 `TopDirectionalLight` `type: "Directional"`、`intensity: 0.7`、`color: "#FFFFFF"`，位于 `[0.525, 0, 3.0]`（桌面正上方 3 m）。光源物体不需要 `MetadataRef`。

注：不同类型光照可能有不同的参数，如直射光可能还有 `direction` 参数用于表示光照的方向，点光源可能还有影响范围、衰减系数等。**本期解析端不读这类附加字段**：`Directional` 与 `Spot` 一律沿该物体局部 **-Z** 发光，朝向完全由 `Transform` 决定（`renderer.ts:addLight`），`Spot` 的锥角/射程尚未实现；这类字段按 §3 原样保留在内存里供后续取用。

前端另有一份**光照预设**常量（2026-10-15 新增，需求规格 §4.8.1 / 决议 **Q77**，`editor/src/lighting.ts:LIGHTING_PRESETS`；**2026-10-20 需求规格 Q114 就地改语义**）：视口工具栏的下拉菜单选中一项，只决定**渲染层实际建哪几盏灯**——它**不写这份文件**。原来那条"把场内所有带 `Light` 的物体删掉并按预设重建"作废，于是本节这张表、这份数据、`scene_version` 与 `scene_sub_version` 全都不动，`/getWorld`、导出与场景摘要读到的**永远是文件自带的那几盏灯**（这正是它从此不进摘要的原因）。预设仍**只写上面这张表里的三个字段**加一个位姿（`type`/`intensity`/`color` + `position`/`quaternion`）——本注里"解析端不读"的附加字段一律不写进预设，免得出现不生效的键；`Directional`/`Spot` 沿局部 **−Z** 发光这条对预设同样成立。文件里那些光源物体在覆盖态下只是**屏幕上不亮**（渲染层把带 `Light` 的节点按覆盖态置为不可见），它们仍在文档里、仍带原来的 id，占位球与标签照旧。空选项 "Scene lights" = 关闭覆盖 = 完全跟随文件。持锁（采集）期内该下拉菜单复位为"跟随场景"并冻结（需求规格 §4.8.1）。

**阴影同样不是这份文件的字段**（2026-10-22 新增，需求规格 §4.8.5 / 决议 **Q117**）：`Light` 仍然只被读上面那三个字段，`MeshRenderer` 仍然只有 `forceOverrideColor`，所以本注开头那句"解析端不读这类附加字段"同样覆盖 `castShadow`/`receiveShadow` —— 文件里**写了也不会生效**，因此不写。谁投影、谁接收由渲染器按灯型与几何来源自己定：`Directional`/`Spot`/`Point` 三族中**在场上实际亮着且 `intensity > 0`** 的灯投影（覆盖态下文档那些灯不亮也就不投），**只有从资产库取回的几何**参与投影与接收，段末幽灵、轨迹路点、灯光占位球与标签、相机视锥线这些编辑层一律不参与。开关是视口工具栏那个「投射阴影」勾选框（界面上 2026-10-28 由 **Q133** 从「投影阴影」改成「投射阴影」，一字之差、字数没变）与 `features.json` 的 `viewport.shadows`，它**不写这份文件**：切换之后本节这张表、这份数据、`scene_version`/`scene_sub_version`、导出与场景摘要全部不动（判据与光照预设同条）。**2026-10-23 起（决议 Q118）这两处是分开的**：`viewport.shadows` 只决定那个勾选框在不在，投不投影由勾选框说了算；键关掉之后勾选框消失，此时改由 `config/constant_config.json` 的 `shadows_enabled` 决定。持锁（采集）期内**只有可见的那个勾选框**冻结为开，理由与上面那句同源 —— 采集像素要可重复；常量那一路每个 tab 读到的是同一个启动值，本身就可重复，没有可冻的控件。

### 4.6 Camera

相机实体，是 `/captureScene`（§4.4）与 `/get2DAABB`（§4.5）的目标。

| 字段 | 类型 | 缺省值 | 本场景取值 |
|---|---|---|---|
| `type` | `rgb` \| `rgbd` | — | 两个相机都是 `rgbd` |
| `fov` | **度**，垂直方向（§2.6） | `60` | `60` |
| `near` | 米 | `0.1` | `0.01` |
| `far` | 米 | `1000` | `10` |
| `resolution` | `[宽,高]` 像素 | `[640,480]` | `[640,480]` |

归一化规则（决议 Q12，`logic.ts:cameraRig`）：缺失或非正数的字段按上表缺省值补齐，且 `far` 至少为 `near × 10`（本场景 `10 ≥ 0.01 × 10`，不触发）；**归一化只发生在渲染层读取时，不回写世界数据**，`/getWorld` 回读到的仍是文件里的原始数值。

- **深度图只对 `type === "rgbd"` 开放**；`rgb` 相机只有彩色图。
- 相机朝向由该节点的世界变换加上 §4.4 的光学系约定（局部 +Z 前、+Y 上、+X 左，决议 Q74）决定，不需要再叠加 Z-up 旋转。本场景俯视相机 `OverheadCameraD435i` 的 `[0.7071,0.7071,0,0]` 是**绕世界 `(1,1,0)/√2` 轴 180°**：局部 +Z 被翻成世界 −Z，于是单位姿态下朝天的镜头改为朝下拍桌面，且**画面上方是世界 +X、画面右方是世界 −Y**。腕部相机 `WristCameraD435i` 的 `[0,0,1,0]` 是**绕父链 Z 轴 180°**：光轴仍沿夹爪的 +Z（接近方向），只把镜头的左右/上下各翻转一次，于是**画面上方是父链 −Y、画面右方是父链 +X**。

### 4.7 RobotDriver

机器人驱动信息。**物体带 `RobotDriver` 即视为机器人**（§8.3，原 `scene.json.scene.robot.id` 概念在新世界文件中不存在）。

| 字段 | 类型 | 说明 |
|---|---|---|
| `joint_sequence` | string[] | 关节角顺序 = TRAJ 前 N 个分量的赋值顺序，单位弧度（§8.3）。关节名必须与 URDF 里的 `<joint name>` 一致 |
| `joint_limits` | `{ 关节名: [min,max] }` | 播放时按此裁剪；超界裁剪并**只告警一次**，不逐帧刷屏 |
| `initial_joint_positions_rad` | `{ 关节名: 弧度 }` | 机械臂初始状态各关节的角度 |
| `now_joint_positions_rad` | `{ 关节名: 弧度 }` | **当前位姿**：它点名的**那几条关节**以这里为准，没点名的仍按上一行的 `initial_joint_positions_rad`；`/updateItem` 重写这份字典即可刷新机械臂的关节位置 |
| `available_connect_joints` | string[] | 表示该机械臂有哪些关节允许继续往下链接其他模型或机械臂 |
| `role` | `"arm"` \| `"passive"`，**可选，缺省 `"arm"`** | **只决定这台 URDF 要不要按机械臂画装饰**（**Q107**，2026-10-19 新增）：`"passive"` 是普通非臂 URDF 模型（微波炉、抽屉柜这类 `type: "model"` 资产），**不画轨迹路点、也不画段末幽灵**（需求规格 §7.3 第 1 条与第 7 条）；其余一切与 `"arm"` 逐字相同 —— 仍按 `joint_sequence` 被 clip 逐帧驱动（§8.3 的"带 `RobotDriver` 即视为机器人"对它照样成立）、仍收 `initial`/`now` 的合并位姿、仍能在 Details 里逐关节**只读查看**（需求规格 §4.8.4 的输入框已由 **Q114** 撤掉）、仍可作为 `RobotAttachment` 的挂载父级或子级（**Q73** 的挂载，以及 **Q80** 当年确认过的"两个方向都能挂"—— Q114 撤掉的是拖动，不是挂载）。字段缺失、`"arm"`、其它无法识别的字符串或非字符串值**一律按 `"arm"` 且不告警**（与 §4.2 `MetadataRef.type` 的宽容口径同族）|

生效方式（`drivers.ts:declaredJointPositions/applyDeclaredJointPositions`、`renderer.ts:buildRobot`）：

- **两份位姿按关节合并**：`now_joint_positions_rad` 只覆盖**它点名的那几条关节**，其余关节仍取 `initial_joint_positions_rad`；两份都没点名的关节**保持在当前角度不动**（新建树时就是 URDF 零位）。`now` 缺席、空对象、值为 `null`、字符串、数字或**数组**时完全不参与（判定见 `drivers.ts:isDictionary`），显示的就是 `initial` 原样。口径来自用户 2026-10-14 的裁决「now 角度只覆盖他提供的关节，没提到的还是 initial」，见 **Q75**；要把某条关节放回初始角，就在 `now` 里显式写出 `initial` 给它的那个值。
- 合并后的那一份（`initial` 打底、`now` 逐条覆盖）在机械臂的 URDF 树建好时**逐个关节落地**，所以载入场景后画面显示的就是这个停放位姿。§4.8 的挂载数值与此**无关**：它是 `parent_link` 的局部位姿，无论机械臂停在哪个角度，夹爪都长在腕上。
- 名字不在该 URDF 里 → 报告一次 `robot <id>: <字段名> joint "<name>" is not in its URDF`（`<字段名>` 是这条关节名**来自哪份字典**，`initial` 或 `now`）并跳过该项，其余关节照常生效；值不是有限数 → 直接忽略该关节。
- 两份位姿**共用同一套落地规则**：限幅按 `joint_limits` 裁剪且只告警一次、`<mimic>` 派生关节跟随源关节（见本节末尾与 **Q69**），`now` 不是一条绕过这些规则的旁路。
- **前端 Details 面板对这份位姿只读**（2026-10-15 曾加入逐关节输入，需求规格 §4.8.4 / **Q81**；**2026-10-20 需求规格 Q114 撤掉该入口，Q81 就地废止**）：面板显示的是下面那份**合并结果**（`drivers.ts:declaredJointPositions()`，`initial` 打底、`now` 覆盖），`(now)` 那条标记保留 —— 撤掉的是"人能往里写"，不是"看得见"。**`now_joint_positions_rad` 这一格照旧存在、照旧参与合并**，写它的人只剩调用方（`/updateItem`）与 Agent；门控那个输入框的常量 `allow_details_joint_angle_edit` 随它一起从配置里删除。渲染层为每个物体算的重建签名读的是**合并后的那份位姿**，所以 `/updateItem` 改 `now` 或改 `initial` 中任何一条会改变合并结果的关节，都会让该物体的 URDF 树重建并把新角度落地。签名里只放这一份位姿，其余 `RobotDriver` 字段（`joint_sequence`、`joint_limits`、`available_connect_joints`）不参与，改了不重建。
- **与轨迹播放的先后关系（**Q76**，2026-10-14 修订 §7.3）**：正常情况下 `/updateItem` 与轨迹播放不会同时出现；播放中收到任何写入（`/updateItem`、`/updateWorld`、面板改动）都**立即退出播放态**，回到正常场景展示，并按文件里那份合并位姿**重新停放机械臂**（`renderer.ts:reparkRobots()`）。反过来，写入之后再发来轨迹相关的调用（`/updateTraj`、`sendFrame`），场景中的物体和关节就归轨迹管了（§8.5）。`/updateTraj` 每帧按 `joint_sequence` 重写这些关节（§8.3），所以播放中的关节角度只由轨迹决定，与这两份字典无关。
- 带 `RobotDriver` 但**没有 URDF 关节树**的物体（例如 `type:"model"` 的普通网格）写了这两份位姿时，效果只是逐个关节报一次"不在其 URDF 里"并跳过，不会改动网格。
- `available_connect_joints` 本期只随 `robotDriver` 保留在内存里，供后续挂载功能取用；当前挂载位姿一律来自 §4.8 的 `transform`。
- **`<mimic>` 联动（2026-10-13 实现）**：URDF 里带 `<mimic joint="…" multiplier="…" offset="…">` 的关节是**派生**的，值 = `multiplier × 源关节的实际取值 + offset`（`multiplier` 默认 1、`offset` 默认 0）。所以 `joint_sequence` **只需命名被驱动的那一条**，另一侧手指自动跟着动；源关节被 `joint_limits` 裁剪时，派生值取**裁剪之后**的源值。解析层只记录关系（`urdf.ts:readMimic`），联动发生在写入层（`drivers.ts:writeJoint`），规格口径见 `Web前端需求规格v3.md` §6.4/§8.4 与 **Q69**。
- mimic 的源关节名写错、或源是一条 `fixed` → **整份 URDF 按 `INVALID_URDF` 报一条诊断**，不是静默跳过：这两种写错的后果都是手指永远不动，藏着矛盾比报错更糟。

### 4.8 RobotAttachment

物体 3 携带该组件，描述夹爪固定在机械臂腕部这一装配关系：

| 字段 | 本场景取值 | 含义 |
|---|---|---|
| `parent_object_id` | `2` | 被挂到的物体 id（UR5eArm） |
| `parent_joint` | `"wrist_3_joint"` | 参考关节 |
| `parent_link` | `"wrist_3_link"` | 父侧 link |
| `child_link` | `"robotiq_2f85_mount"` | 子侧 link |
| `connection_type` | `"fixed"` | 固定副 |
| `transform.position` | `[2.6794892e-09, 0.099999983, 9.7198978e-09]`（即 `[0, 0.1, 0]`） | **在 `parent_link` 局部系里**的挂载偏移：从 `wrist_3_link` 原点沿该 link 的连接轴离开 0.1 m |
| `transform.quaternion_xyzw` | `[-0.7071068, 9.47e-09, -9.47e-09, 0.7071068]`（即绕 X 轴 −90°） | 挂载旋转：把夹爪的局部轴转到腕部连接轴的朝向上 |
| `transform.reference_frame` | `"parent_link"` | 以上数值建立在 `parent_link` 的坐标系上 |

**解析规则（已实现，`world.ts:applyAttachment` + `renderer.ts:worldParentOf`）**：

- 存在 `RobotAttachment` 时，连接位姿由 `transform.position` / `transform.quaternion_xyzw` 决定，且这两个数值建立在 `parent_link` 的**局部坐标系**上；物体 `Transform` 里原有的 `position` 与 `quaternion_xyzw` **一律忽略**（不论是否存在）。本样本物体 3 的 `Transform` 已经只剩 `scale` 与 `parent`，正是下面"写文件的建议"那种写法。
- `Transform.scale` 与 `Transform.parent` **保留**，仍按 §4.1 生效。
- 解析端把挂载记成 `node.attachmentMount = { objectId, link }`，渲染端据此把该 THREE 节点**改挂到 `parent_link` 的 link 节点下**（而不是挂在机械臂物体节点下）。于是机械臂的 FK、轨迹播放、关节拖动都会自然带着夹爪走，无需依赖停放位姿。真机核对（OLS scene 1、`initial_joint_positions_rad`）：夹爪世界 AABB `x 0.231–0.353 / y 0.060–0.208 / z 1.046–1.252`，腕部相机中心 ≈ `(0.29, 0.134, 1.235)`。
- `reference_frame` 的三种取值：
  - `"parent_link"`（缺省，字段缺失或为空串时按它处理）→ 挂到 link 节点，数值按 link 局部系解释；
  - `"parent_object"` → 挂到父物体节点，数值按父物体坐标系解释；
  - 其它值 → 告警 `RobotAttachment reference_frame "<v>" is not a known frame, mounting on the parent object`，按 `parent_object` 处理。
- `reference_frame` 为 `parent_link` 却没写 `parent_link` → 告警 `RobotAttachment framed on parent_link names no parent_link, mounting on the parent object`，挂到父物体节点。
- `Transform.parent` 必须与 `parent_object_id` 一致；不一致 → 退回"把 `Transform` 当普通对象变换"（不记录挂载点），并报告 `RobotAttachment parent_object_id <n> disagrees with Transform.parent <m>, using the plain Transform`。`parent_object_id` 不是合法 uint32 时同样退回并报告。
- `transform` 里 `position` 与 `quaternion_xyzw` 都没有 → 同样退回普通 `Transform`（报告 `RobotAttachment without a transform position or quaternion, using the plain Transform`）。
- URDF 树是**异步**构建的（§5），`syncScene` 那一趟通常还没有 link 节点，所以挂载分两步落地：先挂在父物体节点上兜底，`loadModel()` 建好树后调 `mountOnLinks()` 补挂到 link。补挂必须排在 `built.traverse(child => child.userData.objectId = …)` **之后**，否则子物体会被盖上机械臂的 id；`populate()` 重建树之前也要先 `mountOnLinks()`，把孩子从旧树上摘下来，免得旧树 dispose 时连带销毁子物体自己的几何。**这枚 `objectId` 同时是规格 §4.8.6「一物一盒」的物界判项**（**Q148**）：`worldAabb()` 的递归走到 `objectId` 与本次量测所属物体不同的节点就**停**，于是臂只量臂、手上的夹爪量它自己那一个盒；盖章顺序一旦倒过来，父级就会把孩子盖成自己的一部分、量测重新越界。
- URDF 树里找不到这个 link → 告警 `attachment of object <n> names link "<l>", which robot <id> does not have; mounted on the parent object`，挂在父物体节点上。
- 轨迹播放结束或被中止时的"复位"（`drivers.ts:restoreParent`）复用同一个 `worldParent` 解析，所以挂载关系不会被撤销成"挂回机械臂物体节点"。
- `parent_joint`、`child_link`、`connection_type` 目前只随组件原样保留在内存里，决定挂载点的是 `parent_link` + `reference_frame`。
- **格式变更说明**：2026-10-14 资产重导出之前的样本写的是 `[0.2635845, 0.134, 0.6904584]` / `[0.6830127, -0.6830127, 0.1830128, -0.1830128]`，那组数值等于机械臂停在 `initial_joint_positions_rad`（§4.7）时连接点在**机械臂物体自身坐标系**下的位姿。旧解析器（`applyAttachmentPose`）照着它把数值覆盖到物体自身的 `Transform` 上、父级保持机械臂物体，在停放位姿下与现在的 link 帧写法算出同一个物理位置（可互为校验），但机械臂一动就会脱离腕部；新格式与 `initial_joint_positions_rad` 无关，任何位姿都成立。
- 写文件的建议：既然 `transform` 已承载连接位姿，`Transform` 里就不要再写一份冲突的 `position/quaternion`（保留也无害，解析端忽略）；`available_connect_joints` 目前同样只作为元数据保留，供后续"在允许的关节上继续挂载"的功能取用。

### 4.9 LocalAxes（2026-10-28 新增第九类组件，需求规格 §3 组件定义 + 决议 **Q130**）

**一句话**：物体带这个组件时，视口里画出**该物体自己本地坐标系**的三根轴（+X / +Y / +Z），常驻、不跟选中态走。它是纯叠加层：不参与几何、不参与物理、不改变任何量测，也不出现在任何对外通道的结果里。

> **本节已实装**（2026-10-28）。末条"落点"点名的文件与判据属于实装那轮，测试判据见需求规格 §12.26 —— ① 单测与 ② 负控制已跑（`logic.test.ts` 6 条 + `world.test.ts` 5 条 + `renderer.test.ts` 8 条，共 19 条），③ 真浏览器探针本轮未跑（`tools/browser_smoke.cjs` 仍被 §9.1 身份闸挡住，坑 90）。

| 字段 | 类型 | 缺省值 | 说明 |
|---|---|---|---|
| `length` | number（米） | `0.1` | 三根轴**等长**，各自从该物体的局部原点沿 **+X / +Y / +Z** 画出。不是有限数、`≤ 0`、不是数字 → 告警 `LocalAxes length … is not a positive number, using 0.1` 后按 `0.1` |
| `colors` | `{x, y, z}`，每项一个 CSS 色值 | `{"x":"#FF0000","y":"#00FF00","z":"#0000FF"}` | 逐轴颜色。判据与本文 §4.5 的 `Light.color` 同一条（`#` + 3/6/8 位十六进制，大小写不限）；写 8 位时末两位 `AA` 进材质 `opacity`（小于 1 时同时置 `transparent`），与本文 §4.3 的 `forceOverrideColor` 同族。`colors` 整体不是对象、某个键的色值非法 → **只有那一轴**回到默认色并告警，另两轴照写的走；**键缺失不告警**（本文 §3：字段缺失按默认值回退、不是错误） |
| `show_labels` | boolean | `false` | `true` 时在每根轴末端标 `X`/`Y`/`Z`（沿用本文 §4.5 灯光类型标签那套 Sprite 文字通路）。只有显式 `true` 生效；缺失、`false`、字符串、数字一律按不画且**不告警** —— 与本文 §4.7 `RobotDriver.role` 的宽容口径同族：这是"要不要多画一点"，不是一份数据 |
| `offset` | `[x, y, z]`（米） | `[0, 0, 0]` | 坐标轴原点相对该物体局部原点的偏移。三根轴从**偏移后的原点**出发，方向与长度不变。不是 3 元素数组、或任一分量不是有限数 → 告警 `LocalAxes offset … is not a 3-element array, using [0,0,0]` 或 `LocalAxes offset[i] … is not a finite number, using [0,0,0]` 后按 `[0,0,0]`；**键缺失不告警**（本文 §3：字段缺失按默认值回退、不是错误） |

**取值与生效规则**：

- **原点与朝向就是该物体自己的帧**，不额外叠加 Z-up 旋转（本文 §3 第三条）：四元数为单位阵的物体，蓝轴（+Z）朝天、红轴沿世界 +X、绿轴沿世界 +Y。"这个资产的上是哪根轴"因此是一眼读出来的，这正是本组件存在的理由。
- **轴挂在物体自己的节点之下**，与本文 §4.6 的相机视锥线、§4.5 的灯光占位球同族。于是父链变换、URDF 正运动学、轨迹播放（需求规格 §8.3）与本文 §4.8 的挂载都自然带着它走，**不需要任何一处每帧重算**。
- **长度随父链的 `Transform.scale` 一起缩放，不做补偿**：一个被放大 2 倍的物体，它的局部 +X 走 1 m 就是世界的 2 m，坐标层照这个画出来的才是"它的帧"；补偿回去画出来的那个帧不属于这个物体。本场景所有 `scale` 都是 `[1,1,1]`，这条在这里看不出来。
- **与本文 §4.8 `RobotAttachment` 同物体时**，画的是**挂载之后**那个节点自己的轴：挂载的 `transform.position`/`quaternion_xyzw` 已覆盖物体位姿（本文 §4.1、§4.8），所以夹爪、腕部相机这类挂在 link 上的物体显示的是它装在腕上的真实帧朝向。这是本组件最有用的一种搭配。
- **没有 `MetadataRef` 的物体照样画**：只带 `Transform` + `LocalAxes` 的物体就是一个"纯坐标系标记"，不违反需求规格 §3.7"不得生成占位立方体"—— 坐标层不是任何模型的替代物，它只是叠在场景上的一层线。
- **它是编辑层，因此天生不进采集与量测**：`/captureScene` 的两条 pass（需求规格 §5.10）、视口截图（**Q108**）与录制的默认态（**Q121**）都看不到它；`worldAabb()`、`/get2DAABB`（需求规格 §5.11）、`frame()` 与选中描边都不因它改变；它也不会成为选中项。识别方式与 §4.6 的视锥线同一套 —— 给这一层的挂载节点打一个 `userData.localAxes` 标记（三根轴与标签都挂在这一个 Group 之下，它才是物体节点的子节点），`renderer.ts:isEditorOnly()` 认这一族身份，于是 `hideOverlays()` 与 `expandGeometry()` **两条通路原文一字不改**就覆盖到它（前者按 `isEditorOnly()` 临时按层，后者跳过编辑层 ⇒ 轴不会把自己量进 AABB）。**拾取那一路要跟着认这面标志**：`renderer.ts:1860` 那次 `intersectObjects([...nodes.values()], true)` 是**递归**的，物体节点的子节点本来就会被击中，视锥线"从来不是拾取目标（Q71）"靠的是 `selectable()` 逐父链那一句里的 `node.userData.cameraMarker` —— 本地坐标轴加的就是同一个判断项，不是新分支。**这不是给判据开新口子**：需求规格 §4.8.6 第 4 条立的是同一条证据结构 —— 新层以**一面身份标志**入场，五条对外判据的语义不变。
- **它不跟选中态走，但跟工具栏那枚勾选框走**（与 **Q105/Q106** 管视锥线、占位球的口径相反）：文件里写了这个组件，意思就是"这一层随时可以给我看"，所以不设"选中才显示"这一态。开关有两处（2026-10-28 改口，决议 **Q132**；本条原句"整层唯一的开关是 `viewport.localAxes`、视口工具栏不配勾选框"已按用户口径作废）：**`features.json` 的 `viewport.localAxesToggle`**（原名 `viewport.localAxes`，同日改名）管**工具栏上有没有**那枚「显示坐标轴」的勾选框（**默认 `true`**；界面上那个名字同日由 **Q133** 从「显示本地坐标轴」缩成「显示坐标轴」），**勾选框勾上与否**管**画不画**（**默认不勾** = 不画）。判据 `logic.ts:localAxesEnabled(features, checked)` = **键 && 勾选**，与需求规格 §4.8.6 第 6 条那对包围盒开关同形：键关掉 ⇒ 勾选框消失**且这一层不画**，所以这个键仍是整层唯一的远程出口。**分工**：这一层的**集合**由文件决定（哪些物体带 `LocalAxes`），看不看由那一枚勾选框决定 —— 原句担心的"勾与文件声明各说一套"不成立，因为勾选框从不声称某个物体有帧，它只说这一页要不要叠上那一层。要撤掉某个物体的轴就删它的组件，要撤整层就关那个键。
- **参与该物体的重建签名**（`renderer.ts` 里那份 `JSON.stringify([metadataRef, meshRenderer, light, camera, …])`）：`/updateItem` 改了这份 `properties`，屏幕上立刻出现或消失，不需要重载整个现场。签名里只多这一份 `properties`，与 `light`/`camera` 同格。
- 通用约定照旧（本文 §3）：同一类型重复出现只保留第一个；字段缺失按默认值回退、不报错；`properties` 里未声明的字段原样保留在 `rawComponents`（需求规格 §3.8）。**本期不读、写了也不生效**的两个候选附加字段：`link`（改画该物体某条 URDF link 的帧，而不是物体自身的帧）、`axes`（只画其中几根）—— 按 §3.8 随字典保留，将来实装它们不改本节这张表的名字。

### 4.10 PhysicalProperties（2026-11-12 新增第十类组件，决议 **Q165**）

描述当前模型实例采用的物理属性，适用于带 `MetadataRef` 的模型和机器人。纯灯光等没有模型实体的对象不需要此组件。

```json
{
  "component_type": "PhysicalProperties",
  "properties": {
    "is_static": true,
    "mass_kg": 22.0,
    "friction": {
      "format": "[sliding, torsional, rolling]",
      "values": [0.8, 0.01, 0.001]
    },
    "restitution": 0.05
  }
}
```

| 字段 | 类型、单位 | 含义 |
|---|---|---|
| `is_static` | boolean | 仿真期间是否固定根部。`true` 时不因重力、碰撞或外力移动，仍参与碰撞；`false` 表示允许运动。内部关节仍按 `RobotDriver` 控制。编辑阶段可修改摆放。 |
| `mass_kg` | number，kg | 整个实例的质量。静态时保留此值，不以质量 0 代替静态标志。 |
| `friction.format` | string | 顺序声明，使用 `"[sliding, torsional, rolling]"`。 |
| `friction.values` | 三个数值 | 滑动、扭转、滚动摩擦参数，与资产物理属性定义一致。 |
| `restitution` | number，无量纲 | 碰撞恢复系数，通常为 0 到 1。 |

**继承与覆盖**：组件提供当前实例的覆盖值，未写的字段从 `MetadataRef` 对应资产的 `physical_properties` 继承；`friction` 子字段也分别继承。组件缺失时整体继承资产物理属性；旧资产缺少 `is_static` 时默认 `false`。布尔值使用 JSON 的 `true`/`false`。实例缩放继续使用 `Transform.scale`，此组件不复制资产允许缩放范围 `physical_properties.scale`。

**前端口径（Q165，与 OLS 的"接入状态"对齐）**：这是数据约定，前端**只存、只写，不消费**——不据此做任何物理模拟或渲染。

- **读取**：走 §3.4/§3.8 的未知组件保留路径，整份字典原样留在 `rawComponents`、`toJSON()` 逐字节回吐，不建类型化视图、不归一化、不校验、不拒绝（`world.ts` 因此零改动，`KNOWN_COMPONENT_TYPES` 仍是九类）。
- **写入**：摆放物体或替换机械臂/夹爪/相机/底座时给新物体挂上此组件，`properties` = 该资产 `physical_properties` **逐字复制再删去 `scale`**（与 OLS 自己的场景文件写法一致），并**合并覆盖**到实例已有的同名组件上——资产没声明的键（作者自定义覆盖）因此在一次替换后仍保留。资产即便什么都没声明也照写组件（此时 `properties: {}`）。各字段一律取自资产，前端**不按角色猜 `is_static`、不补默认值**（缺省继承由消费端按 OLS 约定处理）。

**落点（2026-11-12 已实装）**：`editor/src/placement.ts`（`physicalProperties()` 一份纯函数：`{...实例已有 properties, ...structuredClone(资产 physical_properties) 删 scale}`；`armComponents`/`gripperComponents`/`propComponents`/`pedestalComponents` 各追加一项，`placeAsset` 的相机替换、`placeArms`/`placeGrippers`/`placePedestal` 的替换补丁各带上它）、`editor/src/world.test.ts`（原样保留 + 回吐一案）、`editor/src/placement.test.ts`（摆放/替换七案）。**不新增 gateway 调用、不改请求形状、不动 `types.ts`/`contracts/types.ts`**（`ComponentType` 本就是开放联合，`PhysicalProperties` 作为字符串字面量直接合法）⇒ 路由清单与 `audit_parity.py` 探针不增不减。`remountGrippers` 不碰（同一资产重挂，物理属性不变）。

## 5. 模型数据获取：`MetadataRef` → OLS

场景文件**只记 id，不记几何、不记格式**。一个 `MetadataRef` 会换来两样东西：**模型元数据**和**模型具体文件**，且不论是 obj 类模型还是 urdf 类模型都走同一条路：

1. **解析引用**：`path` → `resolveMetadataTarget()` → `{ id, kind }`（kind 为 `model` 或 `robot`，两个 id 空间相互独立）。
2. **取元数据**：`GET {OLS}/model?id=<n>` 或 `GET {OLS}/robot?id=<n>`（`uid` 可选）。返回的是 `{name}.json` 与 `{name}_files.json` **拼接后的单个 JSON**，其中关键字段为 `path`（入口几何文件，模型目录内相对路径）、`is_on_cos`、`reference[]`（该模型继续引用的文件）、`metadata`、`thumbnail`。
3. **取文件**：对入口文件和 `reference` 的每一项各请求一次：
   - `is_on_cos === false` → `GET {OLS}/file?type=<model|robot>&id=<n>&path=<相对路径>`。**`type` 必带且只能是 `model`/`robot`**（缺失或写 `scene` → OLS 返回 400）；OLS 没有 `/file/<id>/<path>` 这种路由，不得臆造。
   - `is_on_cos === true` → 直连云存储 `{cos_base_url}/{path}`，`path` 已是相对路径。
4. **按入口文件后缀分流**（`renderer.ts` 判 `suffixOf(files.entry) === "urdf"`）：
   - `.urdf` → `parseUrdf()` 用 `DOMParser` 解析 XML，`buildUrdfTree()` 建可 articulate 的节点树（joint 节点 + link 节点 + visual）；URDF 里的 `<mesh filename>` 按 `package://<pkg>/` 规则改写为模型目录内相对路径后，仍按第 3 步取文件。
   - `.obj` / `.stl` / `.dae` / `.gltf` / `.glb` / `.fbx` → Three.js 资产加载器，并递归发现其自身引用：OBJ→MTL→贴图、DAE `<init_from>` 图片、glTF `uri`/`basename`。
   - 也就是说：**OBJ 模型与 URDF 模型在场景文件里的写法完全相同**，区别只体现在 OLS 侧入口文件的后缀上。
5. **失败处理**：绝对路径、`../` 逃逸、空字节、非白名单扩展名一律拒绝；贴图 403/404 降级为无贴图（决议 Q7）；缺 mesh/MTL 等必需依赖则整个模型加载失败并报告；**任何情况都不会用占位立方体代替失败模型**（§3.7、§6.4、§6.6）。

OLS 的扩展名白名单含 `.obj .mtl .png .jpg .jpeg .urdf .stl .dae .gltf .glb .bin`（大小写不敏感），`downloadable_types` 决定哪些类型可由 `/file` 下载。
