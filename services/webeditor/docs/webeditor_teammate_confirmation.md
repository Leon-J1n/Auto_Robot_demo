### 2.1 本地增版本不等于逐次上传

优先建议：拖动结束、一次增删或属性编辑确认后，浏览器本地增加版本；不要求每一帧拖动或每次编辑都上传完整场景。下一次提交任务时发送当前完整 Scene，Gateway 向已绑定浏览器实时核验。

如果对方选择“手动编辑期间版本恒定”，我方愿意补做，但至少需要满足以下条件：

1. 每轮处理绑定 `(scene_id, scene_version, sceneDigest)` 的完整快照，并在理解／规划／提交期间保持编辑锁；不能提交后继续悄悄修改现场。
2. 合法手动编辑需失效旧规划的可用状态、旧图像和相关缓存；清理已删除对象的指代，保留仍有效的实例指代和 immutable original。
3. 不能只靠 `(scene_id, scene_version)` 区分任务所用场景。现有 Commands v2 等产物及其消费者需要审计，明确如何绑定到精确快照；不私自修改公共 Commands 结构。
4. unknown／pending、静态部署变化、MetadataRef 替换及 ID 复用等限制继续有效，不因接纳同版本变化而放开。
5. 明确区分 `/startTask` 与 `/commitWorld`：查询和仅生成计划通常不调用 `commitWorld`。因此版本不能笼统解释成“用户提交任务的次数”。

这些是恒定版本方案的支持条件，不是当前已实现能力。确认前仍执行现行严格规则。

### 2.2 摘要范围与跨语言规则

摘要覆盖整个 Scene：`scene_schema_version`、`scene_id`、`scene_version`、`scene_name`、`objects` 及全部组件内容，包括允许的未知组件。忽略对象键顺序，但不忽略数组顺序、当前关节或真实属性内容。

“手动编辑不改版本”与“摘要包含版本”不矛盾：即使版本不变，物体坐标变化仍会改变完整场景摘要。无需为此删除版本字段。

JCS 依据参见 [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785)。双方应规范化同一份已传输 JSON 数据，而不是各自重算坐标后再期待摘要相同：

- `1` 与 `1.0` 作为相同数值会产生相同规范形式；这不允许把严格整数 ID 的类型校验改为任意浮点数。
- `0.1 + 0.2` 得到的数值与 `0.3` 不同，不通过 epsilon、截断或四舍五入强行视为相同摘要。
- 几何计算的容差属于几何校验，不适用于快照摘要比较。
- 不额外做 Unicode 归一化；拒绝不合法 JSON 数值／字符串输入，不用容错替换改变现场内容。

拟补夹具包括：合法数值字段中的整数／小数等价、键乱序、数组换序、浮点差异、Unicode、`now_joint_positions_rad`、未知组件、空 `MeshRenderer.properties={}`、真实 `#FFFFFF` 覆盖，以及仅改变 `scene_version` 的不等摘要用例。未知组件的摘要测试不等于豁免 Brain 的组件引用规则。

### 3.1 ID 分配不能等到下次任务才确认

如果用户“新增对象→删除→刷新”，而高水位只在下一次 `/startTask` 时保存，仍然可能复用删除的 ID。因此要约定：浏览器增物前获得持久分配／预留，或采用同等可靠的预留范围机制；Brain 增物则在持锁、校验高水位的提交路径中协调。

这属于分配元数据同步，不要求把每次手动编辑的整个场景上传服务端。不能同时承诺“所有新 ID 仅存在内存、从不进行可靠预留”与“任意刷新后永不复用”。离线增物能否支持需另行确认，本期不默认为支持。

### 3.2 prepared、rejected、committed、unknown 的证据边界

- `prepared` 表示记录了提交意图，不证明浏览器已经执行，也不证明未执行。
- `committed` 需要与该事务对应的提交证据；Brain 在继续使用场景前仍核对 live 现场。
- `rejected` 需要明确证明该事务未部分修改场景，并且不会随后被旧请求执行。仅超时、没找到回执或浏览器断线，不满足此条件。
- `unknown` 表示无法确定结果，保持不可写并进入核对流程，不按定时器自动变成 rejected。

人工可以参与核对，但“人工确认”文本不能替代必要证据。若当前现场已经发生其他变化，不能强行把旧事务标为成功或拒绝，应保留未决历史并处理现场重新绑定。

### 3.3 我方支持的恢复上限

我方愿意补做方案 B；`/resolveUncertain` 仅为来函中的候选名称，当前没有该接口，本文也不提前锁定未确认的请求结构。

恢复流程至少应能够：保持现场锁定，查明原事务和活动浏览器，排除迟到写入，读取并校验真实现场，再决定继续原会话还是显式建立新会话。恢复结论及证据需持久保存，旧计划不得恢复为可执行。

本期恢复不自动写入旧 checkpoint，不宣称回滚了物理或浏览器操作。继续原会话时不覆盖 original；如确需新会话，应保留旧会话及 original 的历史，不冒充无损续接。

新建 `/sessions`、切换浏览器、重启服务或修改 SQLite 都不能单独构成解锁证据。Gateway 先解除锁、Brain 后恢复或反过来都可能留下中间态，双方必须约定可重试、失败仍保持不可写的协调流程。

### 4.1 相机必须明确选中

当前 UR5e 空模板同时包含 ID4 的腕部相机和 ID5 的顶视相机。“读取现场 Camera 对象”只能得到候选，不能替代选择。不能猜测腕部世界位姿，也不能用另一个相机的图片冒充选定相机。

实际相机／框接口必须绑定活动浏览器、场景 ID／版本／摘要、图像尺寸和非播放状态。采集的 PNG、深度和候选框需要对应同一快照；不支持 segmentation，不生成占位数据。

### 4.2 health 当前到底检查什么

- `service`：AgentService 能处理健康请求，不代表一轮任务已成功。
- `qwen`：访问 `/v1/models` 并检查配置的模型 ID；不是实际推理或视觉能力测试。
- `browser`：对已绑定浏览器调用能力接口和严格 live `getWorld`；未绑定单独显示，不能用其他在线浏览器代替。
- `assets`：对照 OLS 在线目录／元数据与 Brain 本地资源；不等于已经证明浏览器成功加载所有纹理或渲染一致。

当前 browser ready 也不等于会话可写或没有 quarantine，前端不能仅凭健康响应自行解除编辑锁。

### 4.3 部署口径

| 端口 | 服务／用途 |
|---|---|
| 8099 | 正式联调 Gateway |
| 8500 | Brain AgentService |
| 8000 | OLS，读取双方约定的同一版固定资源 |
| 8080 | 现有 Qwen，不修改其运行配置 |
| 8098 | 按对方来函，为 WebEditor 一次性验证栈，不是联调验收对象 |

首期全部本机回环部署。Brain 的配置文件内资源路径相对配置文件解析，运行产物相对启动目录；命令行参数的路径不能未经确认就假设具有同样基准。对方 `constant_config.json` 的加载规则需收到代码后核对。

同意写入只发给绑定浏览器、`getWorld` 不回缓存。没有可应答的绑定浏览器时，同意 Gateway 返回 `503 NO_BROWSER_CONNECTED`。旧 `updateWorld` 可供既有调用方保留，Brain 不调用它；旧接口也不能绕过新写权限和编辑锁。
