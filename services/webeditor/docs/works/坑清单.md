# 开发坑清单（活文档）

138. **接一个"纯数据约定"的新组件，读取端可能一行都不用改 —— §3.4/§3.8 的未知组件保留路径已经就是"原样存进内存"**（2026-11-12，Q165）。用户要"前端读取场景文件时只把数据原样存进内存以备后续使用"，第一反应是往 `KNOWN_COMPONENT_TYPES` 里加一类、建个类型化视图——**错了**。`world.ts:normalizeObject` 把整份 `components` 原样挂上 `rawComponents`（不裁剪、不换算、不拒绝），`toJSON()` 逐字节回吐；不在九类里的 `component_type` 正好走"告警但保留"那条路。OLS §4.10 接入状态原文也是这么要求的：「尚未接入此组件的解析器按未知组件规则保留原始数据」。⇒ 读取端**零代码改动**，只补一条钉住"原样入 `rawComponents` + `toJSON` 回吐逐字相同"的用例即可。**判据**：要求是"只存不消费"时，别建视图、别加 known、别归一化——保留路径就是答案。**② 组件 = 资产 `physical_properties` 逐字删 `scale`，`is_static` 取自资产、别按角色猜**：逐物体核对 OLS 自己的场景文件（`data/scenes/2`），每个实例的 `PhysicalProperties.properties` 恰等于该资产 `physical_properties` 删去 `scale`——`scale` 是资产**允许缩放范围** `[min,max]`，不是实例缩放（实例缩放归 `Transform.scale`），抄进去就错。资产现已普遍声明 `is_static`（臂/爪/相机 false、桌/底座 true），所以**不需要**"臂 movable、桌 static"这种角色推断；资产没声明任何物理属性时也照写组件、`properties: {}`。替换时 `{...实例已有 properties, ...资产副本删 scale}` **合并覆盖**，资产没点名的作者自定义键因此在一次换臂/换爪后仍保留。**③ `ComponentType = KnownComponentType | (string & {})` 是开放联合**：新组件的字符串字面量直接合法，`types.ts`/`contracts/types.ts` 两份逐字节副本**一个字都不用动**（别一看到"新协议字段"就去改 types，先看联合开不开放）。**④ 探针：瞬时 `/getWorld` 504 会被读成"空世界"，静默毁掉 before/after 差分**：一次性网关在重载几何时 `/getWorld` 可能 503/504（坑 131 同族），`getWorld()` 若把"无 objects"一律返回 `[]`，则 `idsBefore` 成空集 ⇒ 摆放后**所有**物体都被当成"新增"；相机 swap 前的 `Camera`/`Transform` 快照成空 ⇒ "换相机不动内参"这条不变性检查被**跳过**却看不出红。修法是**重试读**（拿到 ≥N 个物体才返回）+ 臂过滤只认 `metadataRef.type === "robot"`（被动 URDF 工作台也带 `RobotDriver`，按"有 driver 无 attachment"会把桌子误判成臂）。同族：坑 131（按 URL 排除已归因噪声）、坑 134（判据/夹具要喂线上真值）。

137. **"浏览器收不下"分两种：HTTP 磁盘缓存有单条上限，显式 CacheStorage 没有 —— 别把前者的边界写成后者的结论**（2026-11-12，Q164）。坑 135 ① 那条"服务端与前端都越不过"只对 **HTTP 缓存**成立。`caches.put()` 吃的是 origin 级配额（实测 10.74 GB），48,274,097 字节一条照收，换新浏览器进程、同一 user-data-dir 后 `match` 命中、SHA-256 逐字相同、服务端零命中。**取证必须有那条负控制**：删掉存储条目后再普通 fetch ⇒ 全量重传 2446 ms，证明零请求来自 CacheStorage 而不是 HTTP 缓存捡的。**别走 `Range` 分片那条路**：Chrome 默认的 Simple Cache 后端不支持稀疏条目，**206 响应根本不落盘**，要落盘只能是各自独立 URL 的 200，代价远大于收益。**三条边界写进判据**：非 secure context（`http://<lan-ip>`）下 `caches` 是 `undefined`；默认 best-effort 配额（`persisted()` 为 `false`）可被淘汰；`put` 可能因配额/隐私模式抛错 —— 三处一律 fail-open 退回普通 fetch。**② CDP 看不见 CacheStorage 的读**：它不是网络请求，`Network.requestWillBeSent` 一个事件都不发。所以热启动的正确读数是"72 个 fromDiskCache + 那一份连事件都没有"，**任何"等到 N 个 `/file` 响应"的 harness 都会在这里挂死**，要用网络静默窗口。**③ `expect(...).toEqual(...)` 别用在百万级 TypedArray 上**：8 MiB 的 `Uint8Array` 逐元素深比较，单条用例 **52 s**、11 条把套件从 0.3 s 拖到 **330 s**，而且全绿看不出问题。换 `Buffer.from(a).equals(Buffer.from(b))`（native）⇒ 整套 **344 ms**。字节相等这种判据要用 native 比较，不要用深比较。**④ TS 5.7 起 `Uint8Array<ArrayBufferLike>` 不是 `BodyInit`**：`new Response(new Uint8Array(n))` 报"missing properties from URLSearchParams"这种看着不相干的错。测试里造大字节体直接返回 `ArrayBuffer`（`new Uint8Array(new ArrayBuffer(n)).buffer`），别在 `Uint8Array` 泛型上纠缠。**⑤ 坑 135 ③ 的 CRLF 又咬了一次，而且这次是静默的**：Python 多行 `str.replace` 锚点用 `\n` 写、文件是 CRLF ⇒ **不报错、替换 0 次**，脚本照常跑完，只有 tsc 事后才发现文件根本没变。替换后必须断言命中次数（`count(old) == 1`），不能只看脚本退出码。

136. **`ConnectionAbortedError` 不是 `BrokenPipeError` 的子类：只挡后者，Windows 上的客户端断连会刷出两段叠在一起的 traceback**（2026-11-12，Q163）。浏览器刷新页签／切走会取消在途请求，OLS 写响应时抛 **10053**（跨机）或 **10054**（loopback），而 `server.py` 只挡了 `BrokenPipeError` —— 三者是**兄弟类**（同继承 `ConnectionError`），于是落进宽 `except Exception` ⇒ 打第一段栈 ⇒ 试图往**已经死掉的 socket** 上写 `500 internal_error` ⇒ 第二段栈，日志里那个 `500` 客户端根本没收到。**修法**：`except ConnectionError` 一次覆盖三种，并置 `close_connection = True`；真异常仍照旧 500 + traceback（负控制把宽分支也改成静默吞掉 ⇒ 恰好红那条"真异常仍 500"）。**三个入口都要挡，且两层守卫不能合并**：派发路径写响应（`_dispatch` 内层，**它必须单独存在** —— 少了它，宽分支会先写一次 500，外层再吞也已经晚了）、**派发之前**读请求行／请求头、`OPTIONS` 直写（后两者由 `handle_one_request` 外层负责）。**第二个入口是复现探针逼出来的**：第一版探针发完请求立刻 RST，服务端死在 `rfile.readline`，**根本进不了 `_dispatch`** —— 只修内层会漏掉它。**取证纪律**：模拟"客户端取消"必须用 `SO_LINGER=(1,0)` 强制 **RST**，`FIN`（正常 `close()`）走的是另一条路、复现不出来；想钉"写响应时被掐"就先 `recv(1)` 再 RST。修前/修后同一探针：traceback **12 → 0**、假 500 日志行 **3 → 0**。**顺带自查**：别急着怀疑自己刚加的开销 —— `/list` 每行算版本号在真实库上实测 model 40 行 34.4 ms、robot 11 行 26.5 ms、scene 7 行 3.5 ms，不足以造成断连；`git show <本轮>~1` 逐字比对确认这段错误处理是既有代码。同族：坑 124（断线日志与业务故障是两条链路）。

135. **"零重传"有三个各自独立的天花板：浏览器不收超大单条、harness 等错了信号、CRLF 让负控制锚点一次都不命中**（2026-11-12，Q162）。**① Chrome 磁盘缓存对单个响应有容量上限（约总缓存容量 1/8）**：那份 48,274,097 字节的 `robot 3 / d435i.obj` 每次启动都重传，同一次运行里最大的入缓存条目是 7,313,211 字节的 `tabletop.png`；把 `--disk-cache-size` 提到 1 GB 重跑，读数一字不变。**服务端与前端都越不过它** —— `immutable` 只决定"要不要问"，收不收得下由浏览器说了算。要治只能把那份网格本身变小（减面／换格式）。写口径时不要把这类边界说成"100% 零重传"，把实测的 72/73 与那一条例外一起写进 §6.7／§12.45。**② 取证 harness 的等待条件不能只看 `load`**：第一版在 `goto(waitUntil:"load")` 之后立刻 `setInputFiles`，**冷启动能过、缓存热了以后反而不过** —— JS/CSS 从磁盘缓存秒回，`load` 比 `start()` 里那串 async 更早，文件选择落在 `#scene-file` 监听器接上之前，症状是"树里 6 行、视口空的、`/file` 一个请求都没有"，看起来像缓存把几何吃掉了。正解是等**应用自己就绪的信号**（`#status-primary` 出现 `Connected`）再喂输入，并加一条硬断言"冷启动必须有 `/file` 请求"，否则这种空跑会被当成成功。**同族**：坑 90（smoke 的身份门）、坑 119。**③ 本仓源码是 CRLF，多行锚点用 `\n` 写就一次都不命中**：负控制脚本报"anchor found 0 times"时先查行尾，别急着改判据 —— 正解是读入后 `replace("\r\n","\n")` 做匹配、写出时再回 CRLF，并用 sha256 复核还原。**④ 两条负控制的预期清单本身会写错**：`/list` 去掉 `version` 会连带红既有的 `test_list_model`（契约变了，不是回归）；摘掉 `/assetVersion` 路由**不会**红 oracle 那条（未知路由照样答 `no-cache`）。负控制的价值全在"恰好这些红"，清单错了就等于没做。

134. **判据认的"数据里的词"是夹具编的英文，线上却是中文：整条测试链绿着，产品对每一台线上相机都判错**（2026-11-12，Q161）。`placement.ts:hasCameraTag` 自 Q134 起只认 `tag` 含英文 `camera`，而 `placement.test.ts` 的两枚相机夹具写的正是编出来的 `"d435i,camera"`／`"d455 camera"` —— 判据与夹具互相印证，谁都没碰线上数据。真实 `robot_index.db` 14 条里**没有一条 tag 含英文 `camera`**：`机器人.摄像机` 那两条写 `D435i相机,深度相机,双目,RealSense`／`D455相机,深度相机,双目,RealSense`。于是 `classify` 把每台相机判成道具，点相机走 `placeProp` 摆上桌、现场原相机一台没换，**症状是"切换相机变成摆放物体"**。**修法**：两种写法都认（`camera` 或 `相机`），夹具 tag 换成线上逐字中文，让既有 5 条相机用例直接当回归钉；再按坑 132 的纪律补"上游与本地默认值不同"的用例（英文 tag 仍判相机、中文 tag 的底座 `机器人底座,支架,圆柱` 仍判道具），负控制删掉中文那半句 ⇒ 恰 5 红。**教训**：凡是判据读上游的自由文本（tag、类别名、中文名），夹具必须逐字抄线上响应；"夹具 + 判据都绿"不等于"对线上数据绿"。同族：坑 113／115／132。

133. **"启动时先读权威现场"与"没有浏览器在线就 503"是两条各自正确、合起来必然回空场景的规则**（2026-11-11，Q160）。§5.4 要求 `start()` 在**建 socket 之前** `await loadAuthoritativeWorld()`（这条是对的，坑见该条：`onopen` 再读会被晚到的旧答案抹掉刚摆好的现场）；Q147 又把 `/getWorld` 的 `world_cache` 回退整条删掉（这条也是对的：晚到的上报会把持久身份挪到旧场景，缓存会把它交给正看着别处的读者）。**合起来**：启动那一读问出口时本页 socket 必然还没接上 ⇒ 必然 503 ⇒ `catch` 保持内存空世界 ⇒ 第一次 `onopen` 按"空现场也要报"报上去 ⇒ §5.8"换 `scene_id` 无条件采纳"把**盘上那份也覆盖成 `#0 v0`**。**症状是"刷新回空场景"，但真正的损失是持久身份被空世界顶掉**，刷新后再问 gateway 也拿不回来了。**排查这类问题要同时看两条规则的交点，别只怀疑最近改的 UI**。**第二条**：`get_world` 还有另一条出口 `_session_context(session_id).world_snapshot`，它只在 `_sync_active_conversation_binding()` 里写，要求 **Brain 建成的会话 + 活动历史行** —— 于是"起了 AgentBrain 就正常、只起 OLS + gateway 就回空"。**一个纯前端的现场保存特性不该以 Agent 会话为前提**；判据要专门跑一遍**不起 Brain** 的栈。**修法口径**（Q160）：不是把回退加回来，而是**按读者身份开一个口子** —— 请求头 `X-WebEditor-Browser-ID` 自证为绑定浏览器本人、失败码恰为 `503 NO_BROWSER_CONNECTED`、目标就是绑定浏览器、且缓存四元组 = 持久身份，四条同时成立才答 `X-World-Source: snapshot`。**调用方一个字没变**（它们不带那个头），所以 Q111 的既有判据全部原样绿。**第四条守卫不能省**：`504` 是"权威在但没答"，用旧文档顶替它等于让一个卡死的页面读自己的过去。**第三条附带**：`world_cache` 挂在 `BrowserProfile` 上（Q153），本来就按 `browser_id` 隔离，不必为它新增持久字段。

132. **`docs/OLS接口.md` 里的 robot 类别前缀是错的：文档写"机械臂"，真实索引全是 `机器人.*`**。2026-11-11（Q159）核对三个 `data/<type>_index.db` 的 `SELECT DISTINCT category`：scene 只有 `场景.桌面操作`，model 是 `模型.*` 九条，robot 是 `机器人.单臂/夹爪/摄像机/底座/背景`。而接口文档 `/presignUploadID` 那条写「类型前缀按 type 取 模型/机械臂/场景」。**口径**：类别名、前缀这类"数据里的词"一律以索引/真实响应为准，那份散文只当参考（同族：坑 113/115，以及本轮上方那条 OLS 中文名放置位置）。**顺带一条判据设计的坑**：把界面文字改成"读数据源"之后，如果**回落常量恰好等于数据源今天的值**，那么"读 `机器人.单臂` 得到 `机器人`"这种用例走回落也能过 —— 负控制只红 1 支，说明判据没钉住"真的读了数据"。修法是给用例加**改名/乱序**场景（`现场.桌面操作` → `现场`、`自定义` 排在 `零件.紧固件` 之前 → `零件`），让"读数据"与"背常量"产生不同结果，负控制这才红到 3 支。**凡是"从上游取名字/取顺序"的判据，都要有一条上游与本地默认值不同的用例。**

131. **一次性栈里从面板载入场景后 `/events` 会以 `Invalid frame header` 断开**：console 留一条 error，看着像本轮把 WebSocket 弄坏了。**归因方式要写死**：把本轮改过的源文件 `git show HEAD:<file>` 覆盖回去、**重新 `vite build`、重启一次性栈**（网关启动时才把 `dist/` 拷进临时目录，光改文件不重启读到的还是旧包），再跑同一支探针 —— 2026-11-11（Q158）这样做过，HEAD 侧复现同一串错误，因此与布局改动无关。**纪律**：探针的 `errors` 断言要**按 URL 排除已归因的既有噪声**（这里是 `/events`，以及一次性网关还没有现场时 `/getWorld` 的 503），不要把断言整体放宽成"允许有错误"。**顺带**：`tools/browser_smoke.cjs` 末尾也断言 `errors` 为空，这条噪声会让它在身份闸（坑 90）之外再多一处红，修它属于另一轮。

130. **一个布局事实有两个渲染路径在写时，判据必须收成一个函数、两处都调**：Q157 让资产面板借走 Agent 那一栏，写者是 `.agent-panel.hidden` 加 `.workspace` 的 `--agent-track`。`applyFeatureVisibility()` 只在 `start()` 跑一次，`renderContext()` 每次开合都跑 —— **只接前者的症状是"加载时对、点一下就不对"，而且不抛错**，类型检查和构建全绿。**两条附带纪律**：① `.agent-panel` 自带 `data-feature="agent"`，`[data-feature]` 通用循环会先写一遍 `hidden`，所以专用写者必须排在循环**之后**；② 恢复时要 `removeProperty` 让样式表默认值生效，别写死一个像素数（媒体查询有三档默认值）。**判据写法**：除了"两个路径都调它"，还要有一条"**全文除这个写者之外没有第二处**写这两个东西"的源码级用例，否则下一个人又在别处补一句。**量宽度别写"变宽了"**：让出来的 Agent 栏要与刚打开的左栏分账，真机 1440 宽下是 `995 + 376 - 322 = 1049`，阈值式断言（`> 原来 + 200`）会假红（同族：坑 120/121 的度量边界）。

129. **一个面板挂多个导航按钮之后，"tab" 的身份不再等于 `data-panel`**：Q156 把三个大类搬上导航栏，三个按钮共用 `data-panel="assets"`、只靠 `data-asset-kind-nav` 区分。两处判据都会**静默**出错：① 开合判断若只比 `panel`，从预设场景切到机械臂会被读成"再按一次同一个 tab"，把用户刚要看的面板关掉；② `active` / `aria-expanded` 若只比 `panel`，三个按钮一起亮。**修法**：把 `(panel, kind)` 一起当身份，写成 `logic.ts` 的一对纯函数（`panelTabPress` / `panelTabActive`）供点击与渲染共用，别在两处各写一遍。**取证侧的连带坑**：出厂 `features.json` 里 `navigation.scene` / `navigation.details` 都是 `false`，真机导航栏上**只有**这三个资产按钮，探针里"点一个普通 tab 看看资产按钮是否灭"这一步会等 30 s 超时 —— 普通 tab 的存在性本身是功能键决定的，不能当常量假设（同族：坑 86 的 `hidden` 不是 `count`）。另：一次性网关刚起来还没有现场，`/getWorld` 回 503 并在 console 留一条 error，这不是本轮的运行时错误，断言 `errors` 为空时要按 URL 分辨。

128. **语音模型日期新不代表适合普通话**：官方 Paraformer 2025-10-07 是川渝方言微调版；默认普通话复核应核对模型来源和训练语言，不能仅按日期选模型。两遍识别必须以同一 segment 替换预览，done 放在复核之后；空尾段不再调用离线模型，复核出错阻止自动发送。CPU 复核可能超过原先 10 秒等待，浏览器收尾上限单独延长，连接超时仍为 10 秒。

18. **1.2 MB 的 float32 深度图不能用逐字符 base64**：§5.10 的 `depth_base64` 在 640×480 下是 `640*480*4 = 1_228_800` 字节。`capture.ts` 最初按最直觉的写法实现（`for` 循环 `charAt` 拼 binary string 再 `btoa`），真机端到端 **256~277 ms**，直接超掉 §11.5 的 250 ms 预算；在 node 里把这一段单独拆开计时是 **315 ms**，而改成**分块 `btoa`**（每 8192 字节 `String.fromCharCode(...bytes.subarray(s, s+8192))` 拼接后一次性 `btoa`）只要 **41 ms**，且输出与逐字符版**逐字节相同**（`capture.test.ts` 用 RFC 4648 的经典已知答案 `""/f/fo/foo/foob/fooba/foobar` 加一次 256 字节往返锁死）。两个必须记住的细节：(a) `String.fromCharCode` 收的是**参数列表**，直接 `...整个 1.2 MB` 会栈溢出，所以必须分块，8192 是"单块够小、块数够少"的经验值；(b) 一次 `btoa` 与多次 `btoa` 的**分块边界不影响结果**（base64 是 3 字节一组的流式编码，块长 8192 不是 3 的倍数也没问题，因为拼接发生在编码**之前**）。修完复测 **141/145/154 ms**（翻行+NaN 归一另占 ~12 ms）。另外**首次冷调用是 342 ms**（float 渲染目标与 `EXT_color_buffer_float` 查询的一次性开销），所以真机测耗时至少要丢弃第一次，否则会把"首次"当成"平均"而误判需要再优化。同类测量陷阱：**`btoa(String.fromCharCode(...subarray(0,0)) || "") && (计时段)`** 这种把两段计时串在一个表达式里的写法会被 `&&` 短路，测出"btoa 只要 0.1 ms"的假结论 —— 计时必须拆成两段独立代码，本卡就是这样先得到假结论、重写后才拿到真实的 41 ms。
19. **造透视测试矩阵要先反推 `w` 的表达式，以及"相机量不出 AABB"是个假前提**：本卡两条实测踩坑。(a) `logic.test.ts` 里手写"点在身前"的透视矩阵时，第四列写成 `[0,0,1,-1]` 的**平移分量位置**（列主序 `m[11] = -1`）是对的，但末格 `m[15]` 顺手填 1 就变成了 `w = -z + 1` —— 身后 `z = -2` 的点算出 `w = 3 > 0`，被当成可见参与求交，测试报 `expected 3 to be 2.5`（那个 3 正是 `(-2·-1 + 1)/3` 的错值）。透视矩阵要求 **`m[11] = -1` 且 `m[15] = 0`** 才得到 `w = -z`；造测试矩阵应当从"`w` 该等于什么"倒推每一格，而不是抄一个"看起来像"的数组。(b) 卡片与首版注释都写过"相机没有可渲染几何 → `EMPTY_AABB`"，**这是错的**：§5.11 说"无 `MetadataRef` 的物体用其可视节点/包围体"，而 `renderer.ts` 给相机会挂 `LineSegments` 视锥线（原另有一个 `ConeGeometry` marker，FIX-2026-10-13 起已删，见 **Q71**），`Box3.setFromObject` 照样量得出内容，真机与单测里对相机取 AABB 都返回一个正常的框。`EMPTY_AABB` 的真实场景只有一个：**只有 Transform、没有任何几何的空节点**（§3.7 明确这种物体就是空节点）。同类陷阱：对"移到画面边缘"的**精确裁剪值**做解析式预测也不可靠 —— 本以为 `[2, 1.54, 0]` 会"正好切掉一半"（中心落在 px 0），实际角点在 `x = 1.96~2.04` 上的深度差把中心推到 px −15.16~14.34，断言 `toBeCloseTo(0)` 必然失败；改断**结构性事实**（`clipped === true`、`x_min === 0`、`x_max < 320`、`y_max < 240`）加上**精确的 `aabb_world`**（非对称的 `[1.50, 0.46] ~ [1.58, 0.54]` 足以锁死 Z-up↔Y-up 轴映射），既稳又不丢强度。

23. **`LibraryClient` 的会话缓存最初把**被 reject 的 promise** 也永久存着，导致刷新按钮变成 no-op**：`getJson`/`read` 是 `cache.set(url, request)` 后直接返回，失败路径没有删除动作。两个后果本卡都在真机撞到了 —— ① 点刷新**一条请求都不发**（列表 URL 早已缓存），"刷新资产列表"名不副实；② OLS 重启后同一 URL 仍返回那个旧的失败 promise，面板永久停在"资产列表读取失败"，只能整页重载，而 §12.7 的 DoD 恰恰要求"恢复后可用"。修法见规格 **Q54**：统一的 `cached()` 里 `load().catch(e => { cache.delete(url); throw e; })`（与 `renderer.ts` 的 `models/robots` 同形），外加显式的 `invalidateMetadata()` 给刷新按钮用。**只清 metadata 缓存、不清文件缓存**：文件按 `type+id+path` 不可变，清一次就要重下整台 URDF。
24. **feature 键的"引用判据"必须机械化，且通配删除会连坐只读区块**：`logic.ts:featureEnabled` 是双重语义 —— 父链任一为 `false`/缺失即 `false`，**且目标键本身必须显式为 `true`**。于是 §9.3 里 `panels.details.transform.*` 这类通配清单如果逐字执行（连父键一起删），M6-1 留下的只读区块会整块消失，症状是"选中物体后 Details 只剩一行名字"，看起来像渲染 bug 而不是配置问题。正确做法是把键分成两类再动手：**编辑输入的键**删（`transform.position/rotation/scale`、`visual.*`、`physics.*`、`camera` 的八个输入项、`robot.targets/send`），**只读区块与提示语的键**留（`panels.details.transform`+`.notice`、`panels.details.identity`、`panels.details.robot`、`panels.details.camera`+`.preview`、`viewport.cameraPreview`+`.modes`+`.modes.rgb`+`.modes.depth`）。第二件事是"这个键还有没有人读"不能靠 `grep -rn 'enabled("'` —— 本卡的引用有五种形状：`enabled("…")`、`when("…")`、**反引号模板** `enabled(\`viewport.cameraPreview.modes.${mode}\`)`、`data-feature="…"`、`data-requires-feature="…"`，漏掉后两种会同时产生假 DEAD（把仍在隐藏 DOM 的键当死键）和假 MISSING。模板串取静态前缀参与前缀匹配，再把"仍被引用键的祖先"算作必要键，最后 **DEAD=0、MISSING=0** 才算过。自检脚本一次性的就够，但它给出的 11 个"§9.3 没点名却已失效"的键（`robot.jointNames/positions`、`viewport.tools`、`viewport.tools.select`、`overlays.collider/ifps`、`cameraPreview.{header,close,image,status,metadata}`）必须写进决议（**Q55**），否则下一个人会以为清单是完整的。
25. **§5.13 的码表有两个方向要对账，而"新加一个错误码"有三条出口**：M7-1 的 `tests/test_error_mapping.py` 钉的是**表 ↔ 文档**（`BROWSER_ERROR_STATUS == SPEC_ERROR_STATUS`，25 个码逐个真跑 `/updateItem` 往返）；M7-2 的 `editor/src/error_codes.test.ts` 钉的是**代码 ↔ 表**（正则扫 `editor/src/*.ts` 里 `new WorldError|LibraryError|TrajError("CODE"`，与 `local_gateway.py` 里的表对账）。两边都必须是**相等**而不是包含，否则会各漏一类事故：漏前者 = 表里少一行，浏览器报的码静默落到 `get(code, 502)`（`INTERNAL_ERROR` 就是这么被读成"上游坏了"的）；漏后者 = 新码打错字或把一个渲染期内部码当用户可见码抛出，网关照样答 502 而所有单测仍绿。**新增一个码只有三条合法出口**：① 进 §5.13 + `BROWSER_ERROR_STATUS`（会被 `browser.response` 上报的一切）；② 进 `error_codes.test.ts:RENDER_ONLY` 且**必须同时补一条用例证明它到不了 `browser.response`**（`INVALID_URDF` 是当前的唯一例子：`renderer.ts:loadModel` 把它收成一条 `reportOnce` 诊断，世界文件里只有 `MetadataRef.path`，`addObject` 早已 `ok:true`，异步渲染失败不能倒灌成写失败 —— 给它开一行 400 反而是在宣称"调用方可以按 400 处理一次坏 URDF"）；③ 什么都不做，则 `RESERVED_BY_SPEC`（`SCENE_NOT_FOUND`/`SCENE_NOT_LOADED`，表有码、代码无抛点）之外的第四条断言会红。**另一条同批发现的硬约束**：`rejected_objects[].index` 只能是**提交数组 `objects[]` 的下标**（`world.ts:replaceObjects()` 把 `positions` 传进 `buildHierarchy()`），不能是"存活节点列表的下标" —— 两套下标混在一个字段里时，`OBJECT_NOT_AN_OBJECT` 那条永远正确、后面的层级拒绝每条偏一位，看起来像调用方数错了（详见规格 **Q59**）。`index` 是无 id 条目唯一的定位手段，重复 id 的两条也只有它能区分。
26. **可注入依赖的默认值不能直接写宿主方法本身**：`library.ts:createLibraryClient(config, fetchImpl = fetch)` 是最直觉的写法，也是 Chromium 里的 bug —— 默认参数取的是 `window.fetch` 这个**函数值**，之后 `fetchImpl(url)` 以 `undefined` 为 receiver 调用，浏览器抛 `TypeError: Failed to execute 'fetch' on 'Window': Illegal invocation`。真机症状是资产面板整块空 + `.asset-notice` 显示"资产列表读取失败：scene/model/robot: … is unreachable"，看起来**完全像 OLS 没起来**（本卡第一次跑 smoke 就是这样，先花了很久怀疑端口/stub/CORS）。`globalThis.fetch` 作默认值同样坏，只有包一层才对：`fetchImpl: FetchLike = (input, init) => fetch(input, init)`。**为什么当时 234 例单测全绿却漏掉**（该数字随卡片递增，2026-10-13 为 260 例 / 12 文件）：`library.test.ts` 一律显式注入 `fetchImpl` 假实现，默认参数分支从来没有被测到 —— 这类"默认值即宿主方法"的缺陷只有 E2E 能暴露，同族风险点还有 `postMessage`、`crypto.subtle.*`、`structuredClone` 之外的任何 `window` 方法。自检：`grep -n "= fetch\|= postMessage\|=> fetch\b" editor/src/*.ts`（详见规格 **Q61**）。

33. **异步加载未完时的 AABB 只覆盖"已经到场的少数物体"，据此判断挂载是否生效必然误判**：`/get2DAABB` 与 `renderer.worldAabb()` 量的是**此刻**的几何。FIX-E 取证时 `scene?id=1` 刚载入约 1 秒，`robots/1` 的 20 个 OBJ（≈12 MB）在 `--use-angle=swiftshader` 下还没解析完，于是 `worldAabb(2)`（机械臂）只量到已经进场的子树 —— 夹爪与腕部相机，三个物体的 AABB **完全相同**，看起来像"挂载把三样东西叠在底座上"或"资产坏了"，而这两种怀疑都不成立。正确的判据是**轮询到机械臂 AABB 的 z 跨度 > 0.4 m**（UR5e 停放位姿的竖直尺度）再取值，取回的数据随即自洽（夹爪 `x 0.231–0.353 / y 0.060–0.208 / z 1.046–1.252`，腕部相机中心 ≈ `(0.29, 0.134, 1.235)`）。旁证两条：`/file` 请求 **0 失败**、页面无 toast 报错 —— 有这两条就不该去改资产或加载链路。**口径**：任何"某物体在不在位/挂对没挂对"的真机断言，都要先确认该物体的几何已经进场；同族陷阱见坑 16、21、32（观测时点/环境造成的假缺陷）。

46. **OLS 资产清单里"缺失的文件"只有请求时才暴露，所以回退 `*_files.json` 不等于修好清单**：`data\robots\2\robotiq_2f85_files.json` 在 HEAD 里列 24 项，其中 **8 个纹理 `.png` 已经在 2026-10-14 的纯色化里被删掉**（`.mtl` 只留 `Kd`），而 `reference` 是**请求时**读取的声明清单 —— 没人请求缺项就没人报错，`is_on_cos:false` 也不会去核盘。本轮把 URDF 换回旧模型时，如果只做"`git show HEAD:` 回退清单"，就会把 8 个死路径重新写回资产。**口径**：改资产前先算**磁盘依赖闭包**（URDF 的 `filename` → `.obj` 的 `mtllib` → `.mtl`），用它重写 `reference`；再用**同类清单做横向判据**（其余 13 份机器人清单全部只留 thumbnail 一个 `.png`、零缺失文件 ⇒ "清掉纹理 PNG 引用"是补齐既有口径，不是本轮新发明）。一条 grep 就能自查：`python -c` 遍历各 `data/robots/*/*_files.json`，打印"引用了磁盘上不存在的路径"的条目，只有该修的那份会非空。
47. **`/addObject` 返回 `ok:true` 时网格还没建好，立刻 `/get2DAABB` 会撞 `400 EMPTY_AABB`**：`addObject` 只做世界模型的校验、分配 id、重建父子，`MetadataRef` 指向的 URDF/OBJ 是浏览器**异步**解析并挂到场景图上的，所以响应与"可测量"之间有一个真实的窗口（本轮真机实测约 1 秒级）。症状很容易被读成"刚加的对象前端弄丢了"：第一次跑 `examples/gateway_client_demo.py` 就在第 9 步以 `HTTP 400 EMPTY_AABB: object 12 has no geometry measurable against camera 5` 终止，而 `/getWorld` 里那个 id 明明已经在。**口径**：① 调用方把 `EMPTY_AABB` 当成"稍后重试"而不是"永久失败"，样例因此提供 `get_aabb(client, id, camera_id, attempts=10, delay=0.5)`，并在注释里写明这不是 gateway 的 bug（§5.11 的 `EMPTY_AABB` 定义仍然只针对"没有任何几何的节点"）；② 重试要有**上限**并打印尝试次数，否则 OLS 真挂了会变成静默长等；③ 别用 `scene_version` 来判断"加载完了"—— 版本号在 `addObject` 当场就 bump 了，与资产加载无关。同类判据：**`/captureScene`、`/get2DAABB` 是唯二依赖几何已就绪的路由**，其余路由都在世界模型层面回答，不需要等。
48. **调用方连 `/events` 只许听、绝不能发 `browser.hello`，否则真实浏览器会被摘掉、全线 504**：gateway 的浏览器登记表由 `browser.hello` 建立（`local_gateway.py:_register_browser`），**一条 socket 只有在 hello 之后才算浏览器**；一个"只想看广播"的调用方如果不发 hello，就只会被 `scene.applied` 广播命中（这正是想要的），**如果发了 hello 就成了第二个浏览器**，relay 的写入请求会被定向派给它，而它根本不会执行 ⇒ 每一次 `/updateWorld`/`/addObject` 都等到 `BROWSER_TIMEOUT` 变 504，症状是"我按文档接了 `/events`，结果编辑器整个不能用了"。**口径**：① 样例的 `EventsListener` 只做 `ws_connect` + 收，注释里显式写"never sends browser.hello"，并用测试钉住"这个监听器没有任何出口"（`test_the_events_listener_is_receive_only` 断言源码里 `send_json`/`send_str`/`.send(` 一个都不出现）；② 收到广播要认 `source_browser_id` —— 它指明**是哪台浏览器应答的**，多 tab 时用它区分自己关心的来源；③ 需要"读一次场景"就用 `/getWorld`，不要用 WS 自己发 dispatch（那是 gateway 的职责，`browser_id` 参数已经提供回源定向）。附带一条：**aiohttp 在纯 stdlib 样例里是可选依赖**，`/events` 那步要能缺失即降级（`--skip-events` 或 `ImportError` 都只跳过不崩），否则"只用标准库"的承诺被一步广播绑死。
49. **Windows 控制台默认 GBK，样例不必强推 `-X utf8`，但输出里的字符要挑能编码的**：曾打算给文档型输出用 `§` 并担心 Windows 终端炸 `UnicodeEncodeError`，实测**默认 GBK 就包含 `§`**（GBK 覆盖 ISO-8859-1 之外的常用符号），所以既不需要 `python -X utf8`，也不需要 `sys.stdout.reconfigure(encoding="utf-8")` 这类副作用代码。**判据**：给分发出去的脚本写输出前，用**目标终端的默认编码**做一次真实打印（本轮把探针输出重定向到临时文件后 `python -c` 读回核对），而不是在自己 shell 里跑绿就以为在同事机器上也绿；同理别在 `print` 里塞 emoji 或框线字符（`⚠`/`→` 在 GBK 里也存在风险，`->` 与 `!!` 最稳）。**另一条**：读样例输出做断言时统一按 `encoding="utf-8"` 打开子进程管道（`subprocess` 的 `text=True` 在中文 Windows 上会默认 GBK，把 UTF-8 字节流解成乱码），文件本身仍保持 UTF-8。
50. **`/get2DAABB` 回 200 也可能只量到"半只胳膊"，而且"两次读数一样"不是就绪信号**：**① 形状** —— §5.11 的 `aabb_world` 是 `{"min": [x,y,z], "max": [x,y,z]}`（世界文件自己的轴序，**Q47**），不是角点数组；按 `[[min],[max]]` 写会 `zip` 到 `"min"`/`"max"` 这两个**字符串**上，症状是 `TypeError: unsupported operand type(s) for -: 'str' and 'str'`，而且只在真机跑到那一步才炸（单测里塞的是我以为的形状）。**② 部分几何** —— **坑 47** 只覆盖响亮的那一半（`400 EMPTY_AABB`）；静默的那一半是浏览器**边挂 URDF 边回 200**：刚 `/updateWorld` 之后立刻量机械臂，真机回的是 `[-0.045,0.062,0.533]→[0.045,0.087,0.558]`，即**只有基座立柱**（0.16 m），而整臂是 0.85 m。拿它当"转一圈前应在哪里"的基准，就会在转完之后报 `|start - end| = 788.1 mm` 这种**假失败**——数字没错，错在两端不是同一就绪态。**③ 别指望轮询到"不再变化"** —— 本轮真为此写过 `settled_box`（0.5 s 一发、两次相同即认为稳定），实测它在 0.16 m 处**先暂停、随后继续长大**，判据当场被自己的数据推翻，函数与两条单测一起删掉。**口径**：要做几何判据，就把**两端都放到动作之后测**（转完 2π 测一次、写回 home 再测一次 ⇒ 真机 `|full - home| = 0.0 mm`），扫描前那一发只展示不判据；`scene_version` 与"两次读数相同"都**不能**当作资产就绪的信号。
51. **可重复运行的演示要从"声明的 home"起算，不能从场上 `now` 起算**：一圈动画若写成"读当前 `shoulder_pan_joint`、再加 2π"，第一次跑完世界里就留下 `now = {shoulder_pan: 6.283185}`，第二次要在 `[-6.28319, 6.28319]` 里塞下 4π ⇒ 限位预检直接 `RuntimeError`，**一个本该幂等的样例只能跑一遍**。症状出现的方式也很坑：第一次真机全绿，第二次在第 11 步开头就红，看起来像"上一轮把前端弄坏了"。**口径**：起点取 `RobotDriver.initial_joint_positions_rad`（驱动的基础值，与场上被覆盖的 `now` 无关），限位检查按它算；扫描结束**补一次** `/updateItem` 把关节写回 home，让巡回收尾时世界停在起始姿态。`test_a_second_run_starts_from_the_declared_home` 钉住"起点表达式的来源"（源码级判据，与 `test_the_events_listener_is_receive_only` 同一手法）。
52. **给"要被别人看着跑"的脚本打印，就要显式行缓冲；据此掐时机的取证脚本要防截图排队**：Python 的 stdout 接**管道**（`| tee`、CI 日志、被 `spawn` 收集）时是**块缓冲**，`examples/gateway_client_demo.py` 的全部输出会堆到进程退出才一次性到达 —— 仓库外那个 playwright 编排脚本用"看到 `step 11/15` 这一行"当起跑线掐截图，结果四张 JPEG **全部落在巡回结束之后**（画面是恢复后的空世界，`0 objects`），而同一时刻网关侧 `/getWorld` 明明报 `2.101 rad`。**修法两半**：① 样例在 `main()` 里 `sys.stdout.reconfigure(line_buffering=True)`（分发型脚本的既有职责，不是本轮的临时补丁）；② 取证侧别信截图 —— **headless SwiftShader 下整页截图要几秒**，四张并发会串行排队，判据一律用网关侧读数（角度、`scene_version`）与 `/get2DAABB` 的几何，截图只作旁证；要截就元素级（`locator('canvas')`）+ JPEG，并且**每次只发一张**、等它回来。
53. **轮询周期是下界而非常数，所以"每 5 秒"只能用相邻两拍的间隔来验，不能用"次数 ÷ 时长"**：`local_gateway.py:_agent_poll_loop` 写的是 `await asyncio.sleep(max(1.0, interval))`，而**每一拍还要真跑一次 `GET /queryTaskState` 的往返**（样例服务在自己日志里逐条打 `[http] ... GET /queryTaskState`，这就是免费的时基）。于是配置 5 s 实测落到 **~5.2 s/拍**：本轮真机 4 个任务从提交到全部终态共 **56 拍**，若按"总拍数除总时长"反推周期会得到 5.1~5.3 s 的一个漂移数字，写死成 `assertEqual(elapsed / polls, 5)` 必红。**口径**：验轮询节奏只断两件稳的事 —— ① **终态之后 0 拍**（真机判据：全部 `success/failed` 后再等 7 s，日志里 `queryTaskState` 增量为 0，这一条能钉住"任务表不再被问"这个真实契约），② 巡回里**每个状态各出现过一次**（`created>queued>running>success` 的序列，来自 gateway 侧的广播计数）。次数、耗时、`poll_seconds` 一律只作**观测值打印**（本轮就是打印 `{"polls":56,"poll_seconds":5}`），不进断言。同族陷阱见坑 50（把瞬时读数当判据）与坑 52（headless 截图排队让时序看起来错了）。
54. **要证明"错过广播后能补取"，只能自己把 `agent.job_updated` 丢掉，不能把网关连接整个拆掉**：Q87 的契约是"`/events` 是 fire-and-forget，重连后用**一次** `GET /api/agent/jobs` 补齐"。第一版验证脚本用"杀掉 vite 再起回来"来制造重连，两处致命：① 页面在断连前**已经收到了全部广播**，转录区早就有终态，于是"补取成功后可见"是**假绿**（它测的是推送，不是补取）；② 杀 dev server 会连带把页面变成 `ERR_CONNECTION_REFUSED`，`waitForFunction(/Connected/)` 等到的是重启后的**新页面**，那一页的 `state.messages` 是空的、`state.websocket` 从 `connecting` 起步 ⇒ `caughtUp` 恒为 false，**补取根本不会触发**，症状是"Operations 面板显示 `No Agent operations.`"（而且 `#operations-content` 渲染的是 `state.agentPlan`，任务制之下它本来就不填，见 §5.15），看起来像补取坏了。**正确写法**：`page.routeWebSocket('**/events', ws => { const server = ws.connectToServer(); server.onMessage(m => { if (blind && typeof m === 'string' && JSON.parse(m).type === 'agent.job_updated') return; ws.send(m); }); ws.onMessage(m => server.send(m)); })` —— **只丢这一类帧**，于是同一页面上 `/getWorld` 的 `browser.request`、⑤ 的 `/updateItem`、心跳 `pong` 全部照常，页面自始至终是**同一个**（`state.websocket` 真的是从 `connected` 走到 `reconnecting`）。跑完整轮后先断言转录区**只有 `已创建`**（证明真的丢了），再 `ws.close()` 触发重连、放开过滤，然后才断"恰好一个 GET + 四个终态回到面板"。**判据**：任何"错过 X 后能补回 X"的用语，先问"我怎么让它错过 X 而没顺带错过 Y"。
55. **从 Bash 后台起的验证服务会随 shell 重置一起消失，真机巡回必须用分离进程起**：本轮两次在 `verify.cjs` 跑到一半时撞 `TypeError: fetch failed`（`node --check` 与单测全绿，网关却已经没了）。根因不在脚本：用 `run_in_background` 起的 `tools/serve_verification.py` 与 `agent_service.py` 是**该 shell 的子进程**，会话压缩/工具中断触发 shell 重置时它们被一并带走，`netstat` 上 8097/8500 的 LISTENING 直接消失，而 vite 与 OLS 因为不是同一批起的还活着 —— 症状是"网关半路蒸发、页面挂在 ws 重连"。**口径**：一次性验证栈一律 `powershell Start-Process -FilePath python -ArgumentList ... -WorkingDirectory ... -WindowStyle Hidden -RedirectStandardOutput <log> -RedirectStandardError <err>`（四个服务：OLS 8000、样例 Agent 8500、gateway 8097、vite 5177），起完 `netstat` 逐个确认 LISTENING，收尾按 PID `taskkill`；`-RedirectStandardOutput` 顺带解决"Agent 服务的 `[http]` 行是轮询计数的来源"（坑 53 的时基就落在那份日志里）。**别把它当成"服务自己崩了"去查 gateway**：先看 `netstat`，端口没了就是进程没了。同族的环境侧陷阱见坑 32（多一个 viewer）、坑 35（并发 fetch 被拒连接）。
56. **算夹持中心不能取两个 link 的原点取中点 —— 那是关节坐标系原点，不是指垫接触面**：Q89 之前那版挂载点（`(0, 0.04229, 0.07461)`）就是这么算的，症状是**几何上自洽、画面上不对**：苹果挂在指节之间偏基座一侧，而且 `GRIPPER_CLOSED = 0.72` 这个"看起来合理"的闭合值没人怀疑。**正确做法**是走完整 FK 之后，对 `silicone_pad.obj` 取**贴物面**（该网格局部 `-Y` 那批顶点）的均值当作接触面中心，再取两面中点；两侧 URDF 关于 `rpy z=π` 镜像 ⇒ 中点的 x 必为 0，**x 不为 0 就是算错了的自检信号**（旧值 x=0.04229 已经越出对称面，只是当时没人检查）。顺手可做的量纲对照：driver=0 时两接触面间距应 ≈ 该型号的最大开口（2F-85 是 85 mm，实测 85.40 mm）—— 一个数就能判"这套 FK 读的是不是同一张脸"。**同族**：坑 42（换资产时 link 名是隐形契约）。
57. **`aabb_world` 是"各网格几何盒角点 × matrixWorld 的并集"，倾斜的近球体会把盒子胀大，所以"两个复合盒中心距离恒定"不是刚体判据**：`renderer.ts:expandGeometry/worldAabb` 逐个取 `geometry.boundingBox` 的 8 个角点用 `matrixWorld` 变换后再 union（**坑 20** 讲的是它把视锥线算进父盒，是同一个函数的另一种失效）。后果：`apple.obj` 实测 `74.66 × 74.73 × 71.25 mm`，挂到夹爪上带倾斜时世界盒能读到 `≈108 × 111 × 85 mm`，盒中心随帧漂移，"苹果↔夹爪中心距离"在三个帧上给出 76.4 / 77.7 / 72.3 mm —— 看着像挂载在抖，其实苹果刚体得很（携带段是常量）。**口径**：验挂载是否生效用 ① 苹果盒是否整体**落在**夹爪盒内、② 是否与夹爪盒**共用极值面**（判"在指尖那一端"而不是"在基座上"）、③ 出图看遮挡，三样一起；**别拿两盒中心的欧氏距离当刚性证据**，要刚性就去读携带段的那 7 个浮点本身（离线 `poseAtFrame` 常量段就是铁证）。**同族**：坑 50（`/get2DAABB` 半只胳膊）、坑 33（异步未完的盒）。
58. **两条刻度相关的 CSS 陷阱：靠 `:hover` 才存在的热区等于没有；同色之后才发现"双色"在重叠帧上本来就失效**：Q90 把刻度变成可点的东西时撞上的两件事。(a) 原样式是 `.timeline-tick:hover::after { content:""; …left:-6rem;right:-6rem }`，意图是给 2rem 宽的细线放大点击/悬停区 —— 但 `::after` **只在 `:hover` 成立后才被生成**，而要 `:hover` 成立又必须先命中那 2rem 本体，所以热区永远晚一步、只在边缘抖动。改成无条件的 `.timeline-tick::after` 后热区才真的常驻。**口径**：给小目标补热区，伪元素必须无条件存在（`content:""` + 负 inset），不能挂在 `:hover` 上。(b) 样例 clip 里 step 8 的起点与"苹果挂上"的 Attach **同帧（630）**，step 9 的起点与卸载 Attach 也同帧（750）⇒ 两根刻度位置完全重叠，旧配色下用户看到的是**后写入 DOM 的那根**（attach 在数组尾部，所以看着是黄的），"颜色区分来源"在这两帧上其实一直在撒谎 —— 你看到的黄，蓝的那根也在那儿。统一颜色反而让重叠变得无害。**顺带的判据**：验"两类刻度是否同色"不要看截图，用 `getComputedStyle(node).backgroundColor` 收集成 Set 断言 size === 1，截图上 2px 宽的色差异根本不可靠。**同族**：坑 20（同一处几何被不同消费者读出不同结论）、坑 57（别拿盒中心当刚性证据）。
59. **被 `text-overflow:ellipsis` 裁掉的元素，`scrollWidth` 等于 `clientWidth` —— 用它当"有没有截断"的判据永远读出"没截断"**：Q92 把两个载入按钮搬进视口工具栏后，`#selection-label` 在真机上被挤成 `W…`，而探针报的是 `labelClipped:false`。原因是 `scrollWidth > clientWidth` 这条直觉在 `overflow:hidden` + `text-overflow:ellipsis` 的元素上不成立（Chromium 两者都给被裁后的宽度）。**正确判据**：`const r = document.createRange(); r.selectNodeContents(el);` 取 `r.getBoundingClientRect().width` 作自然宽度，再和 `el.getBoundingClientRect().width` 比。另外这条判据还要**在会挤它的那个面板打开时量**（见坑 60），只在默认页面上量等于没量。
60. **`@media(max-width:…)` 判的是窗口宽度，不是这一栏的宽度；要给"栏"定断点得用容器查询**：本仓的 rem 缩放（`:root{font-size:calc(100vw/1280)}`）与既有断点都挂在窗口上，于是 1440 窗口下 `.viewport-toolbar` 只有 673 px（左栏 + 上下文面板 + Agent 栏吃掉了其余），`@media(max-width:1279px)` 那条"按钮只留图标"永远不触发。修法是宿主 `.viewport-shell { container-type:inline-size }` + `@container (max-width:780px){ … }`，判据换成量栏自身的 `getBoundingClientRect().width`。**两个连带的坑**：① `styles.css` 里**不能写 `//` 注释** —— 不报错，但浏览器解析时会把它后面紧跟的**整条规则**当坏规则吞掉（本卡那条 `@container` 就是这样静默失效的，`document.styleSheets` 里根本查不到 `CSSContainerRule`）；② `container-type:inline-size` 会让宿主成为绝对定位后代的包含块，本仓的 `.viewport-badge`/`#toast` 挂在 `.canvas-wrap` 里所以不受影响，加之前要确认这一点。

63. **"作废令牌"这类计数器，读的地方必须和写的地方同源；`Map.get()` 的 `undefined` 不等于初值 `0`**：Q98 把幽灵从一台改成每物体一台时，`removeGhost()` 给 `ghostGeneration` 写代际、`buildGhost()` 取当前代际传给 `createGhost()`，而 `stale()` 里直接写 `this.ghostGeneration.get(objectId) !== generation` —— 一个**从没被幽灵过**的物体在 Map 里是 `undefined`，与起始代 `0` 不相等，于是**每一次构建都在展开完成的那一刻被判成"已经作废"并当场 dispose**。症状是「幽灵永远不出现，且不报错、不告警、`buildGhost` 一律返回 `false`」，8 个用例同时红。修法是把默认值收进一个函数 `ghostGenerationOf(id) { return this.ghostGeneration.get(id) ?? 0 }`，读写两侧都走它。**口径**：任何"令牌/代际/版本号"的比较，默认值只能有一个出处；`Map.get()` 与 `0`、`''`、`false` 之间的相等性在 JS 里全是坑，尤其是当 `0` 本身就是合法值的时候。**同族**：**坑 20**（同一处判据被不同消费者读出不同结论）、**坑 62**（症状与新功能无关，先怀疑现场）。
64. **swiftshader 下"页面已经死了"长得和"功能没生效"一模一样：`/updateTraj` 504、播放条永远 `hidden`**：Q98 取证第一轮用资产面板点真实的 OLS 场景 3（14 个物体，含工作台、柜子、六个模型、两台机器人），随后推 `examples/scene3_9_segments.traj` —— 播放条不出现，`/updateTraj` 无响应，症状直指"新加的多幽灵代码把页面搞坏了"。实际是标签页在解码 14 个物体的网格时被压垮、WS 断开，网关 `dispatch` 等不到浏览器应答（**坑 55** 那一族的另一端）。**判据**：`/getWorld` 仍能读到那份世界（网关侧一切正常）而页面侧任何 DOM 都不动 ⇒ 页面已死，与功能无关。**口径**：① 取证现场先用**最小可复集合**，且这个集合必须是库文件的**逐字节子集**（本轮用 `GET /scene?id=3` 裁出的 objects `0/14/2/3/7`），不要手搓一份"看起来一样"的世界；② 每个配置档（默认/关断/0.9/0.05/0）**各起一个浏览器**，别在同一个标签页里连跑五轮 —— 五轮的资产解码与两份幽灵实例叠在一起，本身就能把页面压死；③ 需要看清细节时先 `frame` 再滚轮**往外**，往里推会把相机塞进夹爪指缝里（本轮第一版取证图就是这么废的）。**同族**：**坑 62**（先怀疑自己的现场）、**坑 55**（一次性栈要逐个停并 `netstat` 确认）。
65. **aiohttp 的 `client_max_size` 默认 1 MiB，它在我们自己的尺寸闸门之前就把请求体掐了**：Q99 把 `/updateTraj` 改成多条轨迹之后，第一个真实批量（两条 UR5e clip）约 24 KB，一切正常；把两条换成两条 1 MiB+ 的夹具想验证"超 `max_payload_bytes` ⇒ 413"时，拿到的却是一个**不带错误信封**的 413 —— 因为 `web.Application()` 不传参时 `client_max_size=1048576`，请求体在读 handler 之前就被 aiohttp 自己拒掉了。也就是说 §11.1 写的"100 MB 上限"**从 M2-1 起从来没生效过**，单条轨迹时代没人注意是因为一条 UR5e clip 只有 12 KB。**修法只有一行**：`create_app` 里 `web.Application(client_max_size=int(gateway.config["max_payload_bytes"]))`，让唯一的尺寸事实来源回到 `max_payload_bytes`，我们的 handler 检查（`_json_body` 与 `_traj_parts` 各自那条 413）才有机会跑到。**判据/回归用例**：`tests/test_traj_api.py:test_a_batch_beyond_1_mib_reaches_the_handler` —— 两条 1 MiB+4 KiB 的 part、`max_payload_bytes=64 MB`，断言拿到的是 handler 的 **503**（没有浏览器在线）而**不是** 413；只要哪天有人把 `client_max_size` 删了，这条立刻变红成 413。**口径**：① 框架自带的隐性限额（body、消息、超时、并发）必须显式对齐到我们的配置，否则文档与真实行为不一致，而且**症状是"另一个组件报的错"**，排查时会先怀疑自己的校验；② 任何"限额"类断言都要有一条**贴着限额之上**的用例来证明它走的是我们的分支，而不是框架的默认值（§11.1 已把这条写进正文）。**同族**：**坑 2**（通配路由把 API 吞成 200 HTML —— 同样是"框架层先反应，我们的代码根本没跑"）。
66. **畸形 multipart 抛的不是 `ValueError`：`InvalidHeader` 属于 `HttpProcessingError`，而且"0 个 part"这条分支根本不存在**：Q99 的 `_traj_parts` 最初写 `except ValueError`，测试里塞一份 `b"--X\r\n--X--\r\n"`（边界符自相矛盾的 body）直接 **500**。探因要在 handler 里套一层裸 `except Exception` 才看得见：aiohttp 的 multipart 有**两条**失败路径 —— 边界扫描阶段抛 `ValueError`，per-part 头解析阶段抛 `aiohttp.http_exceptions.InvalidHeader`，后者继承 `HttpProcessingError`（`aiohttp` 顶层**不导出**它，得从 `aiohttp.http_exceptions` 引）。**修法**：`except (ValueError, HttpProcessingError)` ⇒ 统一 400 `INVALID_PARAM`。**顺带查出的第二条**：§5.9 原来还写着"body 里一个 part 都没有 ⇒ 400 `MISSING_PARAM`"，而那种 body 在边界扫描阶段就已经抛了，`if not parts` 是**永远走不到的死代码** —— 于是删分支、把 §5.9 的错误码表合并成一句 `INVALID_PARAM`。**口径**：① 文档里每一条错误码都必须指到一段**真能执行到的**代码，"看起来合理但不可达"的分支比没有分支更坏（它会让下一个人在测试里为它写一条永远红或永远假绿用例）；② 第三方库的异常层级**不要靠猜也不要靠记忆**，这个版本里 `InvalidHeader` 既不是 `ValueError` 也不是 `RuntimeError`，唯一可靠的办法是把异常打出来看 `type(...).__mro__`。**同族**：**坑 20**（同一份判据被不同消费者读出不同结论）。

72. **three.js 有两处 `visible` 失明，第二处会造出"看不见的原因引起的 bug"**：**①** `Box3.expandByObject`（`BoxHelper` 的底层）遍历全部子孙且**完全不看 `visible`**，所以把视锥线 `visible=false` 之后，选中描边照样把它算进盒子 —— 屏幕上选中一台 5 cm 的相机却套着一个伸到 `far` 平面的几米大方框，这正是 **Q105** 那句"包围盒永远不再包括视锥"的违反者。**②** `Raycaster.intersect()`（`node_modules/three/src/core/Raycaster.js`）**只检查 `object.layers`，不看 `object.visible`** —— 于是"把占位球隐藏起来"**不等于**"它退出拾取"，默认态下点一片空地会选中一盏看不见的灯。判据：**任何"隐藏 = 不参与"的假设都必须自己过滤**，`pick()` 里那条 `selectable()`（命中项沿父链任一环不 `visible` 即丢弃）不是可选的收尾清理，而是这条失明逼出来的。**顺带一条同族的类型坑**：改用后的描边载体 `Box3Helper` 其 `material` 类型是 `Material | Material[]`，所以 `selectionBox.material.dispose()` 过不了 `tsc`，只能调 `helper.dispose()`。**改法优选"读同一个函数"而不是"再写一套过滤"**：`worldAabb()` 从 **Q50** 起就按 §4.4 排除编辑层，让描边直接读它（`Box3Helper(worldAabb(id))`）就一次性让三个表面（`/get2DAABB`、`frame()`、屏幕）不可能分叉。**同族**：**坑 11**（`/captureScene` 的那份编辑层排除清单 —— 同一批 `userData` 标记，那一条管"不进图"，本条管"不进盒子、不进拾取"）、**坑 57**（`worldAabb` 逐个取 `geometry.boundingBox` × `matrixWorld`，正因为只收几何才不怕嵌套）。

83. **一次性 gateway 读的就是真实 config，用户自己的常量会把基线判据读成"上一轮刚绿的这条回归了"**：`tools/serve_verification.py` 走 `local_gateway.load_constant_config()`（**故意如此**：验证跑的就是生产那份 config），所以用户留在 `config/constant_config.json` 里的 `traj_waypoint_stride_frames: 5` 会原样下发，而 §12.13 ① 的期望值是**按文档默认 `10` 算出来的** 720/10+1 = **73** 个球 —— 本轮第一条红的就是它，实际 `145`（720/5+1），差值恰好翻倍，长得极像 Q101 的步长逻辑坏了。**修法**（与上一轮同一套）：起栈前把该常量**临时顶回 `10`**、跑完**还原用户自己的 `5`** 且不进提交。**判据**：冒烟凡是"按文档默认值算出来的期望数"（§12.13 的 **73/85/43** 三条最典型）都依赖 gateway **启动那一刻**读到的 config，所以起完一次性栈先 `curl -s /api/runtimeConfig` 把那几个常量读一遍再跑；这也解释了为什么这类期望值**不能**改成从 `runtimeConfig` 现读现算 —— 那等于让判据跟着被测常量自己走，永远红不了。**同族**：**坑 22/68**（feature 键同理，改动必须重启 gateway 才生效）、**坑 64**（先怀疑现场再怀疑代码）。
84. **`#toast` 是共享出口、活整整 5 秒，所以"等那段文本出现"不能当"这一次点击已经生效"的同步点**：§12.16 ③ 要连截四张（两个常驻 flag 的四种组合）并比较像素，而 `waitForFunction(/Screenshot copied to clipboard: \d+x\d+ px/)` 在**上一张**的 toast 还没落下去时立刻为真 ⇒ `navigator.clipboard.read()` 读回来的是**上一张 PNG**，于是"四张逐点相同"这种判据**必然空转**（它比的是同一个对象的四次）。修法：每次点击前先 `toastCleared()`（等 `#toast` 重新带上 `.hidden`，元素本身不离开文档，所以 `waitForSelector(..., { state: 'attached' })`）。**判据**：复用应用的通知面做同步点时，等待条件必须包含**"通知已清空"**这一半 —— 只看文本会认上一轮的旧文本；这跟 **坑 81** 是同一件事的两种形状（那里"状态栏文本从上一遍起就为真"，这里"toast 文本从上一击起就为真"），而 ③ 那种"多份产物必须相同"的判据尤其要先证明**产物确实各来自一次自己的动作**。**同族**：**坑 16**（取证要用应用自己的出口）、**坑 70**（每段收尾状态是下一段的前置）。
85. **Chromium 的剪贴板读拿到的是"引用"，应用刚写完立刻读会撞 `InvalidStateError: Clipboard data has changed`**：`navigator.clipboard.read()` 返回 `ClipboardItem` 数组，`item.getType('image/png')` 才是真正取字节的那一步，而 Chromium 在剪贴板**代数又变了一次**时会把手里的引用作废并抛这个错 —— 本应用的写（`clipboard.write()`）落地之后，系统的剪贴板链路上还会再动一下，于是"toast 已经出现 ⇒ 立刻读"这条看起来严丝合缝的同步仍然会撞上。**症状的形状很会骗人**：§12.16 里第一发读（①）绿，第二发读（⑤ 在 `frame()` 之后）红，第一眼像"移动相机把截图搞坏了"，而实际断言根本没跑到。**修法**：把整发读包进**重试**（最多 4 次、每次间隔 300 ms，每次都重新 `read()` 拿当前引用），并且 `catch` **只认这一类错误**（`/Clipboard data has changed|InvalidStateError/`），其余照抛 —— 吞掉全部异常的 `catch` 会把"页面根本没有剪贴板权限"这类真失败读成"重试完还是 null"。**判据**：凡"被测应用自己写、测试再从同一个出口读"的通路，读一侧都要按**可重试的竞态**对待（同一件事在文件读取上是"等 `.hidden`"，在剪贴板上是"重取引用"），固定延时既不够也不稳。**同族**：**坑 84**（同一个 toast 引发的另一半同步问题）、**坑 76**（异步落定要等可判定的中间态）。
86. **本应用所有 feature 关断都是 `element.hidden = true`，节点**不**离开 DOM ⇒ "按钮消失"的判据只能读 `hidden`，不能读 `.count()`**：`main.ts:applyFeatureVisibility()` 遍历 `[data-feature]` 统一 `element.hidden = !enabled(...)`（§9.3 那 85 个键全走这一条），所以键关掉之后 `[data-action="snapshot"]` 依然**在 DOM 里**，`locator.count()` 永远回 `1`。本轮 §12.16 ⑥ 第一版按 `deepEqual([snapshot, frame, loadScene, export], [0,1,1,1])` 写，真机红成 `{"snapshot":1,"frame":1,"loadScene":1,"export":1}`，第一眼像"键根本没接上"（而 ①②③④⑤ 五条全绿，功能明明在跑）。**修法**：判据改成读那一条属性本身 —— `evaluate(node => node.hidden)`，关掉的一侧 `true`、其余控件 `false`。**顺带比 `.count()` 更强的一点**：`hidden === false` 证明"这个控件还在画面上、没被连带关掉"，而 `count() === 1` 连"它其实被隐藏了"都区分不了。**判据**：写"某控件在/不在"这类断言前，先看应用的关断机制是**移除节点**还是**置 `hidden`**（本仓是后者，与 **坑 68** ②"配置生效与否只能从页面侧证据读（诊断行、`label[hidden]`）"同源），判据要和机制同源；`evaluate` 本身要求节点存在，所以"节点还在"这一半不需要再写一条。**同族**：**坑 68**（面板 toggle 与 `page.route` 只拦页面自身请求）、**坑 74**（新需求要先定死唯一可重放表面）。
87. **`/get2DAABB` 的响应体里 `request_id` 每次调用都是新 uuid ⇒ "两次量框必须逐字节相同"这种判据永远不会绿**：`capture.ts`/`aabb` 那条通路把 `browser.response` 的 `request_id` 原样带进 HTTP 响应体，而它是 gateway 每次 `dispatch()` 新生成的 uuid。**症状形状最骗人的一种**：判据写的是 `hash(bodyOn) === hash(bodyOff)`，红了以后先怀疑"线框把盒撑大了"（本卡的命门判据，正是最该红的地方），实际逐字段 diff 只有 `request_id` 那一格在动，`box` 与 `aabb_world` 两态**逐字节相同**。**修法**：解构时把它摘掉再比 —— `const { request_id, ...body } = …`，哈希取 `body`。**判据**：写"同一份现场两次观测必须相同"之前，先分清响应里哪些是**这一帧的量**、哪些是**这一次的邮戳**（邮戳族：`request_id`、`captured_at`；量族：`box`、`aabb_world`、`width/height`、图像字节），摘掉邮戳族之后再相等才算证据；反过来，图像字节里没有邮戳，所以 `/captureScene` 那条判据可以直接整份哈希。**同族**：**坑 33**（先确认几何已进场再取值）、**坑 62**（红了先怀疑判据与现场，再怀疑代码）。

93. **"flex 子项按 stretch 用"这件事没有对应的可计算值 ⇒ 空态判据只能钉宽度，不能钉那个字**：`.agent-empty` 不写 `align-self`，`getComputedStyle(div).alignSelf` 回的是 **`auto`**（不是 `stretch`），容器的 `align-items` 计算值是 **`normal`**（Chrome 对 flex 容器就这么报）—— 两者合起来才产生"占满交叉轴"的**用值**，所以任何"断言计算样式等于 `stretch`"的写法必红（本轮第一次跑到这里就是 `'auto' !== 'stretch'`）。正确的钉法是量结果：`div.getBoundingClientRect().width` 等于容器宽减左右 padding（实测 345.5 = 345.5）。**这条与 §7.4 选 `align-self` 的取舍是同一件事的两面**：分边用 `align-self` 是因为空态**不需要**写任何一条，而不是因为它写了 `stretch`。
94. **`MediaRecorder.isTypeSupported()` 答的是"本机有这一档编码器"，不是"你这条流会拿到什么"**：同一个页面里 `avc1.640028`/`avc1.4d001f`/`avc1.42E01E`/`avc1.42001f`/裸 `video/mp4` 五个字符串**全部回 `true`**，而实际 muxer 交回的 profile 是 High / Main / Constrained Baseline / Constrained Baseline / Constrained Baseline —— 要的是 `42E01E`，拿到的是 Baseline。更要紧的是"支持"与"落盘"之间确实有一段会失败的路：软件 GL 那台配置下 recorder 正常走完 `ondataavailable`/`onstop`、`blob.size` 是 **0**。所以录制这条链的判据只能是**字节数 > 0 且 ffprobe 解得出有限 `duration` 且画面里有东西**，`isTypeSupported` 只用来挑候选（§4.8.7 第 6 条、§12.22 口径 ii）。同族陷阱另见 **坑 102**（把字节从页面搬回 node 时 `btoa` 漏了，好好的 MP4 变成"moov atom not found"，差点反过来怀疑编码器坏了）。
95. **"定时模式 `captureStream(30)` 一帧都不投"这句是误判，2026-10-24 复测作废**：同一条 2 s 带子在活视口画布上 **134,758 B**、在 detached 代理画布上 **9,964 B**、在 attached 代理画布上 **9,480 B**，全是可解码 h264 —— 上一轮那句"103 次 rAF 画出、0 字节"是在**软件 GL 的 0 字节带子**上测的（成因见 **坑 98**/**103**），把环境故障记成了 API 缺陷。本卡仍然用 `captureStream(0)` + 每帧一次 `track.requestFrame()`，但**理由换了**：只有手动投递才能保证"一帧交付 = 文件一帧"，采样钟归浏览器时 `recordReport().frames` 就不是文件帧数的真话，勾选框中途改口径也没法在下一帧立刻生效。教训写在这里给后来人：**"这个 API 在这台机器上不好用"这种结论必须先排除自己那侧的故障**，而且要有第二台配置（`--use-angle=d3d11`）做对照。
96. **WebM 的 `duration` 是 `Infinity`，fragmented MP4 用 seek 取帧会渲染成黑**：Chrome 写 `.webm` 收尾时不回填头部时长，`video.duration` 读出 `Infinity`，于是"时长有限""早帧与晚帧不同"这类判据在 WebM 上**永远不成立**，只能在 MP4 上写（本卡不降级 WebM，正好不必踩）。另一半更坑：`MediaRecorder` 交出的 MP4 是 **fragmented**（`moof` 分片、`stsd` 是 full box 要跳 16 字节头），用 `<video>.currentTime = x` 跳着取帧在这台 Chromium 上渲染出来是**黑的**，看起来像"文件坏了"。诚实的两种读法是 **播放 + `requestVideoFrameCallback` 采样**，或直接把文件交给 **ffmpeg 抽帧**再数像素（本卡用后者，见 `.q121_judge.py` 那套一次性判据）。
97. **"一条画布只有一份画面"这条物理事实换个位置照样成立，但它不再限制屏幕**：本卡初版因为不想每帧多付一趟离屏渲染，就让带子直接录 `#viewport` 那块画布，于是"排除编辑层"只能变成"录制期间把它们从**屏幕上**按住、停止后逐层恢复"，还衍生出"逐帧 hide/show 在 60 Hz 屏上会闪"这条子坑。**用户裁决「录制时按视口截图那套」把方案换成了带子自己那一趟 §4.4 pass**，屏幕因此从头到尾不动一次可见性，那条闪烁风险随之消失——但它换到的东西要写清楚：**每交付一帧多一趟渲染**（`RECORD_INTERVAL_MS` 封顶 30 次/秒）。留在坑表里是因为这两句是同一件事的两面：**画面只有一份，你想让它不一样，就得再画一份**。
98. **整帧平均亮度不是"黑帧判据"，尤其在一个黑背景的现场里**：本卡上一轮用 `ffmpeg -vf scale=1:1` 读整帧均值，判"每一段带子都是黑的"，进而改错了帧源方案、还在正文里写下三条假结论。真相是这个现场是**黑背景里一张小桌子**，一段完全正常的带子整帧平均只有 **4.2/255**（本卡复测同一份正常带子：`lit` 像素 2,262–3,063 个、`maxRGB` 453–582、逐帧 YMAX 有 13–15 种取值）。判"有没有画面"必须换成：**逐帧 `signalstats` YMAX 有没有变化**（相机在动就一定变）+ **全分辨率抽帧数亮像素/特征色像素** + **文件字节**（带线框 1.84 MB vs 不带 38 kB，差 48 倍）+ **用眼睛看那张 PNG**。同族判据失效见 **坑 16**（隐藏页面里 rAF 停摆，"哈希相同"不是"没变"）。
99. **`requestFrame()` 是 canvas capture track 实例上的 own property，不在 `MediaStreamTrack.prototype` 上**：`typeof MediaStreamTrack.prototype.requestFrame` 是 `undefined`，于是给 prototype 打补丁去数投递次数会安静地数到 **0**，看起来像"我们一次都没投"。正确的插桩点是包 `HTMLCanvasElement.prototype.captureStream` 再包返回的那条 track，或者直接读实例属性（本卡的 `track` 类型断言就是这么写的：`MediaStreamTrack & { requestFrame(): void }`，DOM  typings 里没有它）。
100. **`click({ force: true })` 仍然按坐标命中最上层元素**：视口 1280 宽时 Agent 面板压在工具栏上，`[data-action="record"]` 的中心点其实落在面板上，force 点击被面板吃掉 ⇒ 断言"没有下载"变成"录制功能坏了"。取证要么把视口加宽到不重叠，要么用 `page.evaluate(() => el.click())` 直接派发。**但注意**：直接派发会绕过"隐藏宿主收不到用户点击"这一层——`main.ts:1700` 那条委托监听器的 `[data-feature]` 闸门会先把事件丢掉，所以 `viewport.record:false` 那一格（§12.22 ③ D1）**读不到告警 toast**，只能读两个可见事实：没有 `recording:true` 状态行、没有下载；处理函数里的 `enabled()` 是第二道防线，UI 路径上到不了。
101. **录制取证要把"字节稳定性"排在"载入轨迹"之前**：`Load Traj` 之后现场在浏览器侧报 `paused`，而 §9.1 的身份闸只接受 `stopped`，于是 `/captureScene` 回 `camera_frame_scene_mismatch`，"同一次采集在录制中与空闲回同一份字节"这一半就测不到了（与 **坑 90** 同一道闸，那条挡住的是 `tools/browser_smoke.cjs`）。跨模式那一幕（B）又是本卡命门、必须跑，所以判据顺序定死为 **A → C（含采集字节四态对比）→ B → ②**，而不是按需求条目顺序写探针。
102. **把二进制从页面搬回 node：先 `btoa` 再 `Buffer.from(..., 'base64')`**：`String.fromCharCode` 逐块拼出来的是**二进制字符串**，直接交给 base64 解码器会得到"结构合理的坏 MP4"——`ffprobe` 报 `moov atom not found`，看着像录制端坏了、也像容器挑错了，白排查一轮。页面侧 `btoa(binary)` 之后再传，node 侧 `Buffer.from(b64, 'base64')`；顺带 `String.fromCharCode(...大数组)` 会栈溢出，分块 8192（与 **坑 18** 同一条纪律）。下载事件那侧更简单的做法是 `download.path()` 直接复制文件，本卡的 C/D 格就是这么做的。
103. **软件 GL 下带子会交付帧却写回 0 字节，录制取证必须 `--use-gl=angle --use-angle=d3d11`**：同一份代码、同一个现场，swiftshader 那台配置下 `MediaRecorder` 走完生命周期、`blob.size === 0`（这正是 §4.8.7 里那条"0 字节只告警不下载"的兜底被写进设计的原因，也是 **坑 95** 那句误判的源头）。**与 **坑 88** 是一对**：那条说的是 `rgbd` 采集在 swiftshader 下要 13.6 s、预算 15 s 会被吃光；这一条说的是同环境的编码通路直接不产出。凡是取证脚本，命令行参数要写死在这张卡里，不然下一轮又从零猜一遍。
104. **删一整族 CSS 时，最危险的不是要删的那条，而是和它挤在同一行的那条**：`styles.css` 里 `.hidden` 关断习惯写成多选择器共享一行 —— `.session-strip.hidden,.agent-stall.hidden{display:none}`。Q123 撤下 `.session-strip*` 整族时，`old_string` 只要按整行匹配，就会把**同一条规则里的 `.agent-stall`** 一起带走，而 `.agent-stall` 是仍在用的 Agent 卡顿提示。**症状不报错**：类型检查、单测、`vite build` 三件事对 CSS 排版失效一律无感（`tsc` 不看 css，vitest 不起样式，build 只打包不验证选择器），唯一暴露点是真机上那条提示再也收不起来。**修法**：删族时逐条挑，一行里有兄弟选择器就只摘自己那半（本行缩成 `.agent-stall.hidden{...}`）；删完做**两侧**核对 —— 静态侧 `grep` 被删选择器 **0 命中**（顺带发现 `.session-strip #session-camera` 本就是一条打不到任何节点的死选择器），运行侧读**兄弟选择器那条规则的计算样式**还在（`.agent-stall` 的 padding、border-bottom 未丢）。**同一形状的第二个现场**：`main.ts` 的整页 DOM 是一条几千字符的模板字符串，删 `#session-strip` 那个 `<div>` 时 `old_string` 必须带上**兄弟节点**（前一个 `</header>` 或后一个 `#agent-toast`）才能定位，只写目标那一小段容易命中多处、命中错了也不报错 —— 它只会少一个永远为 null 的元素，而 `getElementById(...)` 返回 null 的调用点在下一段代码里才炸。**判据**：凡是"删掉一整套只被一个界面块用到的样式/节点"，收尾验证要**同时**包含"被删的东西确实没了"和"没被连坐的东西确实还在"两条，且后者要读**计算样式或子节点序列**，不能只靠构建通过。**同族**：**坑 72**（同样是"不报错的看不见"）、**坑 68**（判据只能来自页面侧证据）。
105. **落盘成功之后的收尾动作，绝不能把已成功的写入报告成失败 —— `os.fsync(目录)` 在 Windows 连句柄都拿不到**：现象是 Agent 侧一直 `NO_BROWSER_CONNECTED: browser <uuid> is not connected`，而磁盘 `var/gateway_state.json` 里 `browser_id` 写的正是那个 uuid；`GET /api/health` 同时给 `browser.connected:false` 与 `browser_id:null`。**这不是绑定丢了，是登记压根没成功，或者连接被打断了**。**根因**：`gateway_state.py` 的原子写是 `tmp` → `os.replace` → 再 `os.open(parent, os.O_RDONLY)` + `os.fsync` 括一次目录项（POSIX 上这是让**改名本身**进文件系统日志的正确做法）。Windows 对目录给不出这样的可读句柄，`os.open` 直接 `PermissionError [Errno 13]`（本机 `os.name == "nt"`；新建一个临时目录再 `os.open` 三行复现），而它排在 `os.replace` **之后** ⇒ 数据早已落盘，异常只是把"写成功"上报成"写失败"。**它放大成掉线走两条**：`_register_browser()` 里 `bind_browser()` 排在 `self.browsers[browser_id] = socket` **之前**，所以重启后第一次 hello 根本没登记；`apply_state_sync()` → `record_scene()` 是每一帧场景上报都会走的路径，于是每次上报都把 `/events` 那条 WS 打断（异常顺着 `async for` 冒出 `events()`，aiohttp 收掉连接），页面 1.5 s 后自动重连（`main.ts:1556`）再被打断 —— Agent 的请求落在空隙里就是"浏览器没连"。用户那台 8099 的 `var/stack/gateway.err.log` 里 **31 条 traceback 全落在同一行 `save()`**（28 条经 `events()`、1 条经 `_register_browser()`，另有 `get_world`／`_reconcile_brain_session` 各一处）。**修法**：一个模块级 `_fsync_directory()` —— `os.name != "posix"` 直接返回，否则 open/fsync/close 三步照旧；两处写入者（状态文件与 §8.1 的 commit receipt）共用同一个函数，避免"一个改了一个没改"。**判据**（不依赖跑在哪个平台）：把 `gateway_state.os.name` 钉成 `nt` 跑一遍 `bind_browser()` 与 receipt 写入，断言文件真落盘、异常没冒出来；再钉成 `posix` 断言 `os.open(path, os.O_RDONLY)`、`os.fsync`、`os.close` 各恰好一次；**负控制不是新写的**：`tests/test_gateway_state.py:697`（`test_a_browser_that_is_not_connected_gets_the_honest_answer`）与 `tests/test_gateway_sessions.py:1471` 钉的本来就是"没 hello 过的浏览器不算连着"——它们在这一轮第一次真正跑到（修复前整套 python 是红的），live 侧也复验了陌生 `browserID` 仍回 503 `NO_BROWSER_CONNECTED`，所以这条修复没有把报错删掉。**真机侧**用一次性栈（`python tools/serve_verification.py --port 8098 --library-url http://127.0.0.1:8000`，复用用户已在跑的 OLS，不碰他自己的 8099/8500）配一个纯 aiohttp WS 客户端：hello 后 `connected:true`，再发一帧 `browser.state_sync` 后**仍是** `true` 且 `closed:false`、`ping()` 通，`/allocateObjectID` 对绑定中的 id 回 200、对陌生 id 回 503。**同族**：**坑 90** —— "红得不像本轮的锅，于是一直没人碰"：这一条 python 全红（72 失败 / 80 错误）已经跟着回归链如实上报了四轮，每次都写进验证列当"预存在的红"，而它的栈顶在业务代码里 —— 同一行异常也正在打用户真实 gateway 的浏览器连接。**教训**：一条被反复记录的"测试环境红"，只要栈顶落在产品代码，就该按缺陷问一句"线上谁会撞到它"。
106. **撤掉一个 DOM 宿主时，指向它的每一次 `querySelector` 都要同批删掉 —— 它的症状不是报错，是"这块界面再也不更新了"**：Q125 删 Operations 子面板时先删了模板（`<button class="operations">`、`<div id="operations-content">`、`#operation-count`），`updateAgent()` 里那两处写入（`querySelector("#operation-count")!.textContent = …`、对 `#operations-content` 的 `innerHTML`）和点击委托里那条 `toggle-operations` 分支留在原地。`main.ts` 用的是非空断言 `!`，于是每次 Agent 渲染都抛 `TypeError: Cannot set properties of null` —— 而它在**渲染函数中途**抛出：消息列表已经写进去了，后面的 `drawIcons()`、`localStorage` 落历史一起被跳过。**症状逐条对应**：新消息出现但不带图标、刷新后历史不回填、点了没反应，页面控制台才有那一句。**为什么回归链抓不到**：`tsc` 看不见（字符串选择器无类型）、`vitest` 不起整页 DOM、`vite build` 只打包 —— 492 例全绿照样带着这个 bug；只有真浏览器加载页面才暴露。**修法（一条机械步骤）**：删宿主之后 `grep` 该 id／class 字符串**在 `editor/src` 里必须 0 命中**（模板里那一次除外，它已随删除消失 ⇒ 全表 0 才算干净），再刷新一次页面读 `page.on("pageerror")` 为空。**同族**：**坑 104**（删一族 CSS 时最危险的是同一行里的兄弟选择器）、**坑 72**（"不报错的看不见"）—— 三条合起来是同一句话：**模板删除的验证必须是"引用归零 + 一次真加载"，构建通过不算**。
107. **"最后调度者赢"的丢弃规则遇上"同一次点击自己调度两次读回"，会把一条后验判据变成每点必假 —— 判"这次迁移成没成"不能拿"页面此刻相信什么"当证据**：现象是点一次「新建会话」必然弹"会话切换已被取消"，而 Gateway 那边 `POST /sessions` 已经返回 200 和新 id，刷新页面看到的正是新会话（**用户那句"它其实成功了"**）。插日志量到的一次点击：`POST /sessions` **7.203** 答出 `35a22f70…` → `createSession` 里 `await refreshSessionState()` 的那次读回打了版本 6、**7.409** 落地时发现 `sessionRefreshVersion` 已是 7 ⇒ **丢弃自己的正确答案**；版本 7 是这次点击的 `applyWorld(resetDocument)` 触发的 `scene.applied` 回声于 **7.207** 排队的，它 **7.511** 才落地。于是紧接着那句 `state.session?.sessionID !== view.sessionID` 读到的是**上一个会话**（`0c222f66…`），判"被取消"——而 7.511 那次读回证明绑定早已是新 id。**两处都要修，缺一不可**：**① 读回串行化**（`sessionRefreshInFlight` 链式，丢弃规则只保留"答案不得覆盖更新的答案"，落地次序由调度决定；**请求数不增** —— `readCurrentSessionState` 本来就先 `fetch` 再判戳，旧写法并未少发一次，只是把它丢了）；**② 撤下这条后验判据**（对刚由这次 `POST` 建立的绑定，`POST` 才是权威；唯一能取消这次迁移的是**更新的用户选择**，即 `conversationSelectionGeneration`）。只做 ① 时后验判据仍会在别的时序里误伤（回声那次读回更晚落地依然可能），只做 ② 时页面其他入口仍会被丢弃规则打断自己刚排好的读回。**三条可复用的判断**：**(a)** "最后一次调度"≠"最后一次落地"，任何用"最新戳"作废在途结果的规则，都隐含假设**同一动因不会在一次点击里排两次**；**(b)** 校验"我发出的那件事成功了"，证据只能来自那次发出本身的回执或其后必然发生的读回，不能来自"页面当前的信念"——信念是被并发更新的缓存，不是回执；**(c)** 这条 bug 在 `npm run dev` 下**根本测不到**：vite 的 `callerRoutes` 不含 `/sessions` ⇒ 直接 404 走另一条错误分支（**坑 3** 的复发：新增根路径调用方接口必须同批补代理表）。取证因此走一次性验证栈（8098 + `dist/`），且 `#toast` 为空**不能单独**当"没报错"的证据（`showError` 会自动收起），要与 `#agent-toast` 的成功回执和网络面板那条 200 一起读。

113. **"NaN 顶点 ⇒ 网格不画、不可点"是错的前提，坏的是那个被缓存的量测，而全场症状是从相机进来的**：卡 ㊽ 的第一版单测断言"一份带 NaN 顶点的网格射线打不中"，跑红（实际命中 **1** 次）。原因是 three 0.171 **容忍** NaN：`Ray.intersectSphere` 的判别式与 NaN 比较全为假 ⇒ **落空**而不是拒绝，NaN 的包围球因此根本挡不住射线；`Triangle` 那侧把 NaN 的分母读成"平行"⇒ 只是不命中。于是带 NaN 的网格**照画**（有顶点的那些面）、**照样在它有顶点的那些面上可点**，`Mesh.raycast` 与视锥剔除都没意见。真正被打断的是**量测**：`computeBoundingBox`／`computeBoundingSphere` 第一次被问就把 NaN **缓存在几何上**，这一个数随后被 `worldAabb()`、`/get2DAABB`、§4.5 描边、§4.8.6 线框与 `frame()` 共用；`frame()` 把它写进 `orbit.target`／`camera.position`，**从那一刻起整台视口的每一条射线都打空**，健康网格一起遭殃 —— 这才是用户那句"**有时候**点不中"的机制（不是随机，是"frame 过之后"）。**落法**：判据按真实机制写 —— 断言"完整那个面命中 1 次、丢了顶点那个面命中 0 次"这一对，而不是断言"整份网格不可点"；修复落在量测侧（`repairExtents` 只从有限顶点量 + `expandGeometry` 里 `isFiniteBox` 那个判项），而不是去改 `raycast`。**可复用的判断**：给"某个值坏了 ⇒ 某个功能失效"写断言之前，**先把那个值喂进真实库函数看一眼**，不要按直觉推断库会怎么防御；NaN 在图形库里几乎从不是"拒绝"，它是"比较全为假"，而全为假常常意味着**放过**。**同族**：**坑 19**（造测试矩阵要先反推 `w`，别抄一个"看起来像"的数组）、**坑 112**（读数错的时候先怀疑探针）。
114. **搬动 OBJ 的声明之前，先看那份文件用不用负数索引**：OBJ 的正索引是**绝对的**、从文件头数起，所以把 `v`/`vn`/`vt` 整体排到第一条面之前**不改变任何正索引指向谁**（卡 ㊿ 就靠这一句把 6 份 robotiq 零件解析成完整网格）；但 `-1` 的意思是"**此处**已声明的最后一个顶点"（`OBJLoader` 按 `index + len/3` 解、`vt` 用 `len/2`），搬动声明会**悄悄**改掉它指向的顶点 —— **不报错、不产生 NaN，只是一份形状不对的网格**，比原来的 NaN 更难查。**落法**：重排与规范化必须在**同一遍**里做完 —— 每个负数索引写成它已经意味着的那个绝对索引（`declared[slot] + value + 1`），就地已越过文件头的那个（`absolute < 1`）保持断掉、不替它造顶点；此后"声明写在哪儿"对任何文件都不再有意义（出厂库 0 份用负索引，这一手是给以后的资产买的保险）。**可复用的判断**：任何"重排输入行"的规范化，先问一句**这套语法里有没有相对引用**（`-n`、行号、偏移、`$-1`、相对路径），有的话**重排与消相对必须同一遍**，否则第二遍再也分不清哪些是原来的、哪些是被搬过的。**同族**：**坑 115**（判据的宽窄）、**坑 4／12**（"错了但不报错"那一类）。

118. **广播出去的"确认帧"要能被读者认出是不是回给自己那一次的，而认的办法只能是读者自己发的号**：确认帧走 fan-out（`scene.applied` 发给所有连接），所以"这一帧答的是谁的那一次写"**帧本身原本答不了**——旧帧只有四元组 `(scene_id, scene_version, scene_sub_version, sceneDigest)`，读者只能拿它跟自己手里的四元组比，而这一比**分不出"晚到的自己"与"别人的写入"**，两者的正确处置却正好相反（前者要丢，后者要信并应用）。于是连点场景 1→2→3 时：gateway 广播前要 `await _ensure_automatic_session`（Brain `POST /sessions`，Brain 忙就等到超时）⇒ 2 的回声可以晚到用户已经在 3 上；旧 `adoptWorld()` 只有"四元组相同⇒重报／不同⇒重读 `/getWorld` 整份覆盖"两条路，晚到那一帧走重读 ⇒ **旧场景盖回刚加载好的新场景**；接着 `reportWorld()` 把旧场景推回去，而"换场景无条件采纳"让 gateway 也认了 ⇒ **两边一起钉死**，不再像以前那样下一次重连自愈；`if (adoptingWorld) return;` 还把重读期间到达的**新**回声整帧丢掉 ⇒ 最后那次确认永远不来。**修法**：让**发起方自己编号**（`browser.state_sync.payload.report_seq`，页面生命、从 1 起、**不持久化**），中转方**逐字回声**（`scene.applied.ack_report_seq`）并**不解释、不比较、不持久化**这个数，读者按四支判：会话号两边都有且不等 ⇒ 先重问一次 `/api/sessionState` 再判（`session_switch` 恢复历史那一帧的新会话号可能比本页轮询先到），仍不等才丢；号**小于**自己最大号 ⇒ 晚到，丢；**相等** ⇒ 确认，只刷会话与状态栏（不动世界、不重读、不重报）；**`null` 或更大** ⇒ 信并应用（`null` = 不是浏览器上报落地的：调用方写入／`/commitWorld`／`session_switch`；更大 = **同一 `browser_id` 的兄弟 tab** 写的——`BROWSER_ID` 是 `localStorage` 里的持久号，同一 profile 的两个 tab 共用它，所以按 `browser_id` 定向广播**分不开它们**，能分开的只有这个号）。落地期间到达的帧**只留最新一帧入队**（`queuedAdoption`），绝不 `return` 掉。**判据三条**：① 广播式确认帧要区分"晚到"与"别人的"，只能靠**发起方的号**，靠状态快照比不出方向；② 号**绝不持久化**——刷新后的页面若拿着一个对端从没见过的号，会把自己第一条回执读成"别人写的"；③ 中转方只回声不解释，才能做到**对 Agent 侧无感**（AgentBrain 走几乎相同的应用路径，且 Agent 任务中不允许切场景）。**同族的另一半**：这一轮同时把 `/getWorld` 的 `world_cache` 回退删了（`X-World-Source` 只剩 `live`）——跨场景无条件采纳之后，一次缓存读数足以把"晚到的回声"升级成"两边都同意的旧场景"，见坑 32 的"前提已改"。**同族**：**坑 117**（覆盖式回读只放在用户还不能操作的那一刻）、**坑 32**、**坑 87**。

122. **URDF 整机 AABB 的最低点不一定是机械臂的承重底面**：弯曲手臂可能有 link 几何低于根部固定底座，整机盒的 `min.z` 会因此把支架摆得过低；metadata AABB 也可能在根部底面之下。支架定位应从根 link 沿固定关节量底座视觉几何，遇可动关节即停；无法可靠量测时才回退整机盒。显示上的整机轴对齐并盒还会覆盖关节间空域，逐 link 显示可缩紧视觉边界，但 `/get2DAABB` 等调用方仍须使用相同 link 盒的并集。
123. **一个用户动作还没写完时，第二个动作不能换掉它正在改的整份 World**：空现场的首次桌面摆放要先异步加载 baseline；两次快速点击如果都在空 World 上看见 `objectCount === 0`，就会各自加载并 `applyWorld()` 一份 baseline。先开始的摆放继续改旧 World，后开始的 World 留在 `state.world`，于是前一个已成功的物体在下一次 `renderer.syncScene()` 后消失。即使桌面已初始化，多个完整世界快照也可能并发上报：跨 WebSocket 的 `browser.state_sync` 在版本检查后等待自动会话，再落盘，旧报告若晚恢复会覆盖新现场；连接断开/重连时更容易触发。**修法**：把同页库面板改动排成一条失败可恢复的异步队列；gateway 将 state_sync 的判定、异步会话准备与持久化包在同一串行区。**判据**：第二个摆放开始前第一个必须完成；旧报告在准备期间暂停、新报告随后到达时，最终缓存和磁盘都必须是新报告。Vite `ECONNABORTED`/`ECONNRESET` 是连接断开的信号，不是覆盖原因本身；要同时检查 WebSocket 生命周期与断线后的权威回读。
124. **`/events` 的断线日志与场景消失是两条独立链路**：浏览器重连期间旧 socket 的 `close` 回调可能与新 socket 的生命周期交错，Vite 代理会把客户端主动断开显示成 `ECONNABORTED` / `ECONNRESET`。这类错误不能作为场景覆盖的根因；应先保证重连定时器单例、忽略旧 socket 回调，再让代理对这些断线码静默。嵌套相机的点选还必须从真实注册节点回溯，不能只信任模型子网格继承的对象 id。
125. **把浏览器 profile 隔离只做在 WebSocket，HTTP 仍读全局状态，串台会从另一条入口回来**：本轮最初把 `browser.hello` 分区做对，却漏了 `GET /getWorld`、Agent jobs 和 `/sessions` 的 HTTP 上下文；两个浏览器各自连上后，调用方请求仍落到 gateway 默认 profile，表现为页面偶尔读到另一台设备的现场。正确口径是浏览器所有 gateway HTTP 请求都带 `X-WebEditor-Browser-ID`，在 middleware 入口选择 profile，之后所有 handler 继续读既有 `self.state`／`self.pending` 属性；AgentBrain 的字段不改。另一个容易反着修的点：`browser_id` query/body 是既有业务断言，不能被 middleware 当成隐式路由覆盖 header；同一 profile 的重连还要在新 socket hello 到达前摘掉旧 active socket，否则测试客户端会把第一条请求发给已关闭连接。**同族**：坑 32（第二个 viewer 抢答）、坑 87（消息身份与业务内容分开）。
