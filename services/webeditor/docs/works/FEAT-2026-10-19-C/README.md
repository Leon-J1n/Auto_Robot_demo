- **Q103 = 两份各自独立的 v2 文件，骨架不动、只有"怎么动"变**：新脚本 `examples/make_scene3_variants.py` 一次产出 `examples/scene3_wrist_first.traj`（**23912 B**，9 段 / **840 帧** / 60 fps，次序 **远端 → 近端** `wrist_3 → wrist_2 → wrist_1 → elbow → shoulder_lift → shoulder_pan`，六个目标角 `1.35 / -0.85 / 0.60 / 1.25 / -0.95 / 0.55`，第 8 段回拧 `shoulder_pan` 到 `1.80`，时基沿用 `PRE_ROLL 30 / MOTION 60 / PAUSE 30`）与 `examples/scene3_alternate_joints.traj`（**17892 B**，9 段 / **610 帧**，次序 **远近交替** `elbow → wrist_1 → shoulder_pan → wrist_3 → shoulder_lift → wrist_2`，六个目标角 `-1.85 / 0.95 / -0.65 / 1.45 / 0.70 / -1.20`，第 8 段回拧到 `-1.20`，时基一并改密 `25 / 45 / 20`）。**"方便区分"是需求不是装饰**：三份跑的是同一个世界子集、同一台臂、同一个夹爪、同一套 attach/detach 语义，能分辨"现在播的是哪一条"的只有**次序 + 角度 + 总时长**，所以第二条连时长都改 —— §7.1 的下拉框标签是 `<名称> · <帧数> · <fps>` 而本地条目用**文件名**，两份同系列文件只差帧数时，让长度不同是最便宜的可分辨性（§12.4c 的刻度根数与播放头读数因此各自不同：`0 / 839` 对 `0 / 609`）。**9 段骨架、挂载第 7 段末 / 卸载第 9 段初一字不动**，于是 §8.4 的 FK、§8.6 的 Attach、**Q89** 的抓取 offset、**Q98** 的两台幽灵、**Q101/Q102** 的叶子臂路点对新文件**自动适用，前端零改动**。**为什么另起脚本而不改 `make_scene3_traj.py`**：`scene3_9_segments.traj` 是**已发布验收数字的载体**（§12.4b 的 11 根刻度与 `0 / 839`、§12.12 的六帧浓淡差值、§12.13 的 85 个路点），改它 = 重算三处取证；新脚本只**按名字复用**与"某一份具体 clip 无关"的那些事（`POSE_DIM`/`WORLD_ROOT`、三个物体 id 与三份家位姿、夹爪闭合角、`ObjectTrack`、`smoothstep`/`ramp`/`hold`/`read_back`），老脚本与旧文件**一字未动**（`python -X utf8 examples/make_scene3_traj.py --out` 仍可逐字节重建）。
- **本轮真正的技术发现（坑 69）：复用生成器 = 连带复用它的"这一份 clip 的常量"**。第一版直接 `from make_scene3_traj import encode`，结果 610 帧那份在**文件头第 4 个字**里声明的是 `TOTAL_FRAMES = 840`，而症状不是报错 —— 是"播放条能拖到 839、840 帧之后的每一帧都停在末帧姿态"，人眼看着像轨迹跑完了。修法是新脚本自带一份 `encode_clip(objects, attaches, total_frames)`：逐字照抄布局（`<8I>` 头 + index 记录 `<IIHH>` + 7 分量默认位姿 + 每段 `<IIII>` + attach `<IIII>` + data 区）**只把总帧数变成参数**。判据写进 **Q103**：**次序/角度/时基/总帧数属于 clip，布局常量属于格式**。自检靠 `read_back()`（它读的是文件里的头而不是内存里的常量，所以正好能抓住这类"声明与字节不一致"），加上 `tests/test_traj_examples.py` 里"三区必须恰好铺满文件"那条（`attach_at + 16*attach_count + data_bytes == len(blob)`）。
- **Q104 = 多选语义"整批按选择顺序追加 + 选中这批的第一条 + 全有或全无"，实现是零新解码路径**：`#traj-file` 加 `multiple`，`loadTrajFile(file)` 换成 `loadTrajFiles(files)` —— `N` 份文件读成 `N` 段字节、拼成一个 `Uint8Array`，交给**未改动一字**的 `applyTrajRequest()`，请求形状与调用方 push 完全同构（`payload:{count:N, byte_lengths:[…], byte_length:总和}`）。于是"一次一个文件"就是 `N=1` 的特例、行为与今天逐字节相同（§4.3 明写这条兼容句）。**为什么不循环调 N 次单条**：Q99 定了浏览器只按 `byte_lengths` 切、不读切片头部，也定了全有或全无；循环 N 次等于自己实现一条"第 k 次失败则前 k-1 条已生效"的部分生效路径 —— 下拉框条目和用户手上的文件对不上，比整批失败难查得多。**为什么选中这批的第一条**：与 Q100"整批替换回到第 0 条"同构，是用户唯一能背下的规则；单选时"第一条"就是刚选的那个文件，与 Q100 原文自然重合。**坏文件点名到文件名**：批量失败消息带 `trajs[<i>]` 下标，手动通路知道自己那份 `FileList` 的顺序，`main.ts:trajFileMessage()` 把下标换回**文件名**再进 toast（调用方通路只有下标 —— 文件名只在浏览器侧有意义，Q100 的"不进 wire"照旧）。**`#scene-file` 不加 `multiple`**：世界只有一份，`applyWorld()` 是整份替换语义，一次选多个世界文件的结果就是最后那份覆盖前面几份，纯噪声。
