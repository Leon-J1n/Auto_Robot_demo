# docs/works —— 任务记录制度

> 2026-11-05 起生效。取代旧的"单文件进度管理"（`Web前端实施计划.md` §4 任务卡 + §9 PLAN_STATE、`UI优化记录表.md`、需求规格 §13 决议记录逐轮追加）。旧文件均已归档到 [历史档案/](历史档案/)，原路径只留迁移提示。

## 新任务怎么记录

**每次任务在 `docs/works/` 下新建一个文件夹**，文件夹名用 `YYYY-MM-DD-主题短语`（同一天多轮就加后缀 `-a`/`-b`）。文件夹里必须有一份 `README.md`，至少包含三节：

```markdown
# YYYY-MM-DD 主题

## 原因
为什么做这件事：用户原话 / bug 现象 / 上游变更。写清触发点，别写实现细节。

## 做了什么
实现口径与落点：改了哪些文件、关键判据、决议号（如果修订了规格）、明确"不做"的边界。

## 进度
| 项 | 值 |
|---|---|
| 状态 | 进行中 / 已完成 / 受阻（原因） |
| 完成日期 | YYYY-MM-DD |
| 落地 | commit 或分支 |
| 验证 | 跑过哪些命令、结果如何 |
```

收尾时：
1. 把 `进度` 一节更新为最终状态（完成的文件夹不再改动，除非后续任务改判它——那时在新任务的文件夹里写清改判关系）。
2. 在 [INDEX.md](INDEX.md) **顶部**加一行索引。
3. 踩到新坑就往 [坑清单.md](坑清单.md) 加一条。
4. 如果任务修订了规格口径，直接改 `docs/Web前端需求规格v3.md` 对应小节（就地修订，保留 Q 决议号溯源），不要把规范文字写进任务文件夹。

## 冷启动（新会话按顺序做）

1. 读 `docs/Web前端需求规格v3.md` —— 现行口径的唯一需求权威。
2. 读 `docs/场景文件描述.md` 与 `docs/ur5e_table_empty.json` —— 世界文件格式与真实数值样例。
3. 读 [INDEX.md](INDEX.md) 顶部几行 + `git log --oneline -10`，确认最近做到哪。
4. 读 [坑清单.md](坑清单.md)。
5. 开工前 `git status` 确认工作树没有他人在途改动。

引用格式约定：`file:symbol` = 文件加符号名（如 `local_gateway.py:create_app`）；规格引用写作 `§5.9`（指需求规格 v3）。

## 禁令（沿用旧实施计划 §8，避免破坏既有决策）

- **不要**修改用户维护的输入件：`docs/ur5e_table_empty.json`、`tests/fixtures/scene_example.json`、`docs/OLS接口.md`、`docs/轨迹文件布局描述.md`、`docs/Web前端最新要求.md`。
- **不要**改写已归档的历史决议原文（`历史档案/` 里的内容是冻结的）；要推翻旧口径，就在规格 v3 里就地修订、并在当轮任务文件夹里写清推翻关系。
- **不要**为"未来可能需要"预留抽象层。
- **不要**用 `any`/`@ts-ignore`/`as unknown as` 绕过 `contracts/types.ts` 的类型错误。
