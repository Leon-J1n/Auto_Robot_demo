## 任务卡原文

### FEAT-2026-11-02-A —— 世界原点那三根轴改站进仿真系：`AxesHelper` 与 `simWorld` 同一个倾斜角（**Q135**；口径与实装同一张卡；依赖 Q105、Q108、Q130、Q131）

- **起因（用户两句话，第一条是只读检查）**：「帮我检查一下，世界坐标轴（viewport.worldAxes）是如何绘制的，每个轴是什么颜色」⇒ 检查结论是**两件不同的事被这一句问在一起**：**颜色**——`THREE.AxesHelper(1.5)` 建完从不调 `setColors()`（全仓库零处调用），用的是 three 内置的**每轴顶点色渐变**（`node_modules/three/src/helpers/AxesHelper.js`：X `1,0,0`→`1,0.6,0`、Y `0,1,0`→`0.6,1,0`、Z `0,0,1`→`0,0.6,1`，材质 `vertexColors:true` + `toneMapped:false`），又因 `renderer.outputColorSpace = SRGBColorSpace` 输出，尖端在屏幕上比这几个数值看着更亮；这与 §4.8.6 的 `LocalAxes` 是**两套色**，那一族默认是 `logic.ts:LOCAL_AXIS_DEFAULT_COLORS` 的纯色 `#FF0000`/`#00FF00`/`#0000FF` 且可按物体声明，世界原点这两根没有任何字段能声明它。**系**——helper 与 `GridHelper` 一样在构造时 `scene.add`、**不在 `simWorld` 里面**，于是它画的是渲染系（Y-up）的 +X/+Y/+Z：屏幕上**朝天那根是绿的**（文件 +Y 换算过来正好落在渲染 +Y）、**蓝的那根指向文件的 −Y**，与 `LocalAxes`（单位姿态物体蓝轴朝天）以及 `docs/场景文件描述.md` §3 那句"渲染根 `simWorld` 自带 -π/2 的 Z-up 旋转"在同一张视口里互相指认不同的方向。用户据此下达第二条：**「修改世界坐标轴的绘制代码使其与仿真系保持一致」**。
- **口径与实装同一轮**：`docs/Web前端需求规格v2.md` **就地修订 §4.4** 那条 Q131（新增"三根轴站在哪个系里"一段：换算式 `文件 +X→渲染 +X、+Y→渲染 −Z、+Z→渲染 +Y（朝天）`、颜色事实、**网格明确不转**的理由），**§12.27 新增 ⑤**（判据 F 条 + 夹具限制 + 负控制 + 实测数字），新增决议 **§13.48**（Q135 行）。**`docs/场景文件描述.md` 本轮不改** —— §8 那条禁令只允许在"文档与已实现行为互相矛盾"时按实现事实改那几行，而该文件从未断言过世界原点轴朝天是哪一根颜色（§4.9 末那句对照说的是这族家具不归场景文件管），§3 那句本轮之后**反而更成立** ⇒ 没有矛盾要修，画法口径记在规格里。
- **实装形态（一处常量、两句赋值）**：`renderer.ts` 把构造 `simWorld` 那句字面量 `-Math.PI / 2` 提成 `export const SIM_WORLD_TILT`（`toSceneBox` 上方，注释写清它是"世界文件与渲染系之间唯一的那一次换算"），`this.simWorld.rotation.x = SIM_WORLD_TILT` 与 `this.axesHelper.rotation.x = SIM_WORLD_TILT` 各用它一次。**为什么是"同一个常量"而不是再写一个 `-Math.PI/2`**：同源这件事从此可以断言（`axesHelper.rotation.x === simWorld.rotation.x`），而两处字面量一致只是巧合。**为什么不给网格也转**：`GridHelper` 自己的 XZ 平面就是文件的 `z=0` 地板，转了反而要把那一圈格子重新解释一遍。**为什么不把 helper 挪进 `simWorld`**：收益一样，但要重新解释 `hideOverlays()` 遍历 `scene` 与 `isEditorOnly()` 那条通路 —— 一句 `rotation.x` 就够，改动面小得多。**颜色一字未改**：用户要的是系不是色，且渐变随几何一起被转，"哪根什么色"在换算前后都成立，变的只有"哪根朝天"。
- **顺带作废一条自己写过的断言**：`toSceneBox` 上方那段注释原先说 `simWorld` 带着"图里唯一的旋转"。本轮之后那是假的（两处共用同一个角），按"文档与实现互相矛盾就就地改口"的规则同轮改写，不留矛盾措辞。
- **单测（568 → 569 例 / 18 文件，+1，落在 §12.27 那个 `describe`：5 → 6 条）**：新那条 `stands the three arms in the 仿真系, the frame every node of the document is drawn in` 判两件事 —— **①同源** `axesHelper.rotation.x === simWorld.rotation.x`；**②换算** 把该倾斜四元数乘到三根单位轴上，`+X→(1,0,0)`、`+Y→(0,0,-1)`、`+Z→(0,1,0)`，即文件的 +Z 落在渲染系的朝天方向。**夹具限制在册**（§9 PLAN_STATE 卡 ㊴ 那条早已接受的口径）：本族单测走 `adapterFixture()` 手搭的两棵树，构造函数里的初值不在单测覆盖面里 ⇒ 夹具为 `simWorld` 与 `axesHelper` **各补一行**同源赋值，所以新那条测的是"同源 + 换算"，不是"构造时确实转了"。导入表添 `SIM_WORLD_TILT`（常量导出因此有了测试面）。

- **③ 真浏览器未跑**（同卡 ㊶/㊴/㊵：未起 OLS／gateway／dev 三件套，`tools/browser_smoke.cjs` 自 S5-a 起仍被 §9.1 身份闸挡住，**坑 90**）⇒ "朝天那根现在是蓝的、绿的那根落在文件的 +Y"这条**只有单测与代码路径证据，没有像素数字**。要像素的话，最小探针是把默认相机摆到文件的 +X+Y 象限截一帧，核对朝天那根的色族 —— 这一步等用户放行再跑。
