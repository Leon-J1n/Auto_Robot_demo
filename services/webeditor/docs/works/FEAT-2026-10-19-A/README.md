## 任务卡原文

### FEAT-2026-10-19 —— `/updateTraj` 改多条轨迹（`trajs` + `count`，Q99）+ 工具栏轨迹下拉框（Q100）（新卡 ㉒；依赖 M2-1、M4-*、M6-3、FEAT-2026-10-17-B）

- **起因（用户原话）**：「修改/updateTraj接口，添加count参数，原有的traj参数修改为trajs，现在其他调用方有可能传递多条轨迹。在中间的工具栏中添加一个下拉框让用户选择播放哪一条轨迹（默认第一个）。不适用轨迹v3，每条轨迹都是一个单独的v2轨迹。」三个关键取舍用提问钉死，用户选定：**① 线格式 = `multipart/form-data`，每条轨迹一个 part**（不是拼接 octet-stream，也不是 base64 进 JSON）；**② §5.12 响应换成 `trajs` 数组**，顶层平铺的 8 个字段消失，**破坏兼容由用户明确接受**；**③ 下拉框切换 = 整批换、回到 0 帧**。"不使用轨迹 v3"是硬前置：§8 的 v2 布局一字未动，`docs/轨迹文件布局v3(草案).md`（用户自有文件）与本项目无关，多条轨迹＝**N 份各自独立的 v2 文件**。决议记 **§13.28（Q99）** 与 **§13.28（Q100）**，正文就地修订 **§4.3**、**§5.3**、**§5.9**、**§5.12**、**§5.13**、**§7.1**、**§7.3**、**§9.3**、**§11.2**、**§12.4**（新增 **§12.4b**）、**§13.28**。**`features.json` 80 → 81 键**（新增 `playback.trajSelector`），`docs/feature-inventory.csv` 与 `docs/api-inventory.json` 随之重生成。
- **一条请求怎么变成浏览器里的 N 条**：gateway 把 N 个 part **拼成一个二进制帧**下发，`browser.request` 的 text 帧带 `payload = {"count": N, "byte_lengths": [n1…nN], "byte_length": 总和}`；浏览器**只按 `byte_lengths` 切**，绝不去读切片开头的轨迹头（切片边界是唯一事实来源），每片走**未改动一字**的 `decodeTraj`。为什么不改成 N 个 WS 帧：§13.7 **Q34** 定的"一个 text 帧配一个 binary 帧"是 `pendingBinary` 单槽配对，动它等于重开通道协议，而拼接只花一次拷贝。**校验分工按"谁看得见谁判"**：`?count=` 与 part 数是否相符 ⇒ **gateway**（唯一同时看见两者的一方）；`byte_lengths` 与实际帧长、切片偏移是否越界 ⇒ **浏览器**（`GATEWAY_FRAMING_ERROR` 502）；magic/version/`pose_dim`/截断 ⇒ 解码器自己。**失败口径：全有或全无** —— 任何一条解码失败，整个请求带着 `trajs[<i>]: …` 的下标前缀失败，且**内存里已有的那份列表一字不动**（与 **Q49** 同源；半批生效会让下拉框的条目和调用方手上的文件对不上，比整批失败难查得多）。
- **§5.12 的形状**：`{"ok":true,"count":2,"trajs":[{"index":0,fps,total_frames,duration_seconds,object_count,attach_count,ignored_objects,warnings}, …]}`。八个字段的语义与旧平铺版**逐字相同**，只是每条多一个 `index`（0 起，对应请求 part 顺序）、少一个 `ok`；`count` 恒等于 `trajs.length` 也恒等于 part 数。响应里**没有选中态** —— 哪条在播是浏览器本地的事（文件名同理，只有浏览器知道，所以它进下拉框标签、不进 wire）。旧 `application/octet-stream` 请求体**硬 400**，没有兼容期（`traj` 单数名是最可能的调用方笔误，错误消息里直接点名 `multipart/form-data` 与 `trajs`）。
- **本轮真正的技术发现是 gateway 的两处既有硬化**（与多条轨迹无关，一直存在，只是被这个功能照出来）：**(a) 文档里的 100 MB 从来没生效过** —— aiohttp `web.Application` 的 `client_max_size` 默认 **1 MiB**，且在路由之前就把 body 掐掉，所以任何超过 1 MiB 的 `/updateTraj` 批量都会拿到一个不带错误信封的 413；`create_app` 现在显式传 `client_max_size=int(gateway.config["max_payload_bytes"])`，回归用例是 `tests/test_traj_api.py:test_a_batch_beyond_1_mib_reaches_the_handler`（两条 1 MiB+4 KiB 的 part ⇒ 走到 handler 拿 503，而不是 413），§11.1 就地补了这一段。**(b) 畸形 multipart 是 500 不是 400** —— 边界扫描抛 `ValueError`，但 per-part 头解析抛的是 `aiohttp.http_exceptions.InvalidHeader`（继承 `HttpProcessingError`，**既不是 `ValueError` 也不在 `aiohttp` 顶层导出**），原来的 `except ValueError` 接不住；改成 `except (ValueError, HttpProcessingError)` 之后 §5.9 的口径才成立。**顺带清掉一条不可达分支**：§5.9 原来写"0 个 part ⇒ 400 `MISSING_PARAM`"，实测那种 body 在边界扫描阶段就抛了，`if not parts` 永远走不到 ⇒ 删分支、§5.9 的错误码表把两种 400 合并成一句 `INVALID_PARAM`。
- **浏览器侧的改动刻意只做加法**：`state.trajs: TrajEntry[]`（`{traj, name}`）+ `state.trajIndex`，而 `state.traj` 改成**读 getter** —— 于是 `main.ts` 里 `frameIndex`、`poseContext`、Details 的轨迹提示、`ghostTargets` 四个下游消费者**一字未动**就自动跟着选中的那条走。`setTrajectory(list, index)` 是"新批次"与"切换"共用的**唯一**路径：暂停播放、`playIndex` 归 0、重建 `TrajFrameProvider`/刻度/幽灵/重新停放，最后 `renderTrajSelector()`。三条进路的差别只在递进去什么：调用方 push ⇒ **整批替换 + 选中第 0 条**；本地 Load Traj ⇒ **追加进同一份列表并选中自己**（`name = file.name`）；下拉框 `change` ⇒ 同一份列表换下标，**零请求、`scene_version` 不动**。`<2` 条或 `playback.trajSelector` 关断时 `#traj-select` 是 `hidden` 而不是空列表 —— 一个只有"轨迹 1"的下拉框是噪声；`applyFeatureVisibility()` 末尾补一句 `renderTrajSelector()`，让"条数"这条规则压过通用的 `[data-feature]` 显隐循环。
- **测试（vitest 348 → 350 例 / 14 文件，python 171 → 177 例，全绿）**：`scene_requests.test.ts` 新增三例（同一份夹具拼两条 ⇒ 按 `byte_lengths` 切出 `[0,1]` 且各 720 帧；批量描述对不上 ⇒ `count` 与 `byte_lengths.length` 不符 / 缺 `byte_lengths` / `count=0` / 偏移越界 / 总和偏短，五种都 502 `GATEWAY_FRAMING_ERROR`；第二条坏 magic ⇒ 整批失败且消息含 `trajs[1]`）。`tests/test_traj_api.py` **整文件重写为 19 例**（`io.BytesIO` 手搓 multipart：一条 part 一个 text 帧 + 一个 binary 帧、两条拼一帧、旧 `traj` 单数名拒绝、空 part 拒绝、非 multipart 拒绝、`count` 与 part 数不符拒绝、超 `max_payload_bytes` 413、>1 MiB 能进 handler）。`tests/test_caller_demo.py` 的传输用例改断 `/updateTraj?count=2` + `Content-Type: multipart/form-data; boundary=` + 两个 `name="trajs"` + 两条 part 的**先后顺序** + 全文不含 `base64`。`tools/audit_parity.py` **52 → 53 项**（媒体类型探针从两条扩到三条，中继探针改推两条 part 并断拼接后的 `count`/`byte_lengths`/单帧字节）。
- **真机取证（一次性栈：gateway 8099 + vite 5188 + 它自己拉起的 OLS 8000）**：`node tools/browser_smoke.cjs` **13 项全绿**。§12.4b 为了让"哪条在播"肉眼可判，批量推的是**两份不同的夹具**（`tests/fixtures/robot_grasp.traj` 720 帧 + `examples/scene3_9_segments.traj` 840 帧），实测 `{"count":2,"trajs":[{index:0,total_frames:720,duration_seconds:12,ignored_objects:[]},{index:1,total_frames:840,duration_seconds:14,ignored_objects:[{object_id:7,reason:"OBJECT_NOT_IN_SCENE"}]}],"miscounted":"INVALID_PARAM","halfGarbage":"trajs[1]: magic is 0x00000000, expected 0x5452414a"}` —— 两条 part 各回一份 §5.12 摘要、**第 2 条对同一个世界的 `ignored_objects` 判定没有污染第 1 条**；下拉框两行 `轨迹 1 · 720 帧 · 60 fps` / `轨迹 2 · 840 帧 · 60 fps`、默认选中第 0 条；播到 200 帧再切换 ⇒ 读数回到 `0 / 839`、刻度从 **5 根换成 11 根**，切回第 1 条 ⇒ `0 / 719` 配 5 根（整批换、回到 0 帧，**没有"保住当前帧号"**）。两条被拒的批量：`?count=3` 配两条 part 由 gateway 挡在下发之前（错误消息 `count=3 but the body holds 2 trajs parts`）、第二条写成 32 个零字节 ⇒ 整批 400 `TRAJ_INVALID_MAGIC` 且点名 `trajs[1]`；**两次拒绝之后下拉框仍是那两条、选中项仍是 `0`、播放头没动**（Q49 全有或全无），只推一条时该元素 `hidden === true`。本地 Load Traj 追加 ⇒ 标签变成 `robot_grasp.traj · 720 帧 · 60 fps` 且自动选中自己。全程 `scene_version` 一个没动。另有 `dropdown_shot.cjs` 单独拍工具栏（`q100-dropdown.png`：`Load Scene | Load Traj | 轨迹 1 · 720 帧 · 60 fps ▾ | …`，单条时该元素 `hidden === true`）。取证脚本这一族的**截图稳定性**记一笔：headless swiftshader 下 `#traj-select`、`#timeline` 的 element screenshot 会卡在"waiting for element to be stable"直到超时，页面级 `page.screenshot` 同样超时，只有 `.viewport-toolbar` 这类静态容器能拍 —— 与 **坑 64** 同族（现场问题，不是功能问题），断言一律走 DOM 读数而不是像素。
