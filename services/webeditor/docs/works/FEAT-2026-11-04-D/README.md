## 任务卡原文

### FEAT-2026-11-04-D —— 相机画面悬浮窗的第二轮：窗更小、可拖动、名称在上、去掉尺寸读数、RGB／深度切换、深度用伪彩色（**Q139**；口径与实装同一张卡；依赖 Q138、Q136、Q105、Q96）

- **起因（用户原话，一次给全六个动作）**：「把相机画面略微缩小，悬浮窗可拖动，相机名称移动到图像上方居中，不再显示缩略图的大小，添加一个切换按钮用于显示RGB或深度，深度图使用伪彩色」。这是对卡 ㊺ 那扇窗的第二轮口径，不是新一层功能。
- **口径与实装同一轮**：`docs/Web前端需求规格v2.md` **就地改写**六条（§4.8.9 的"内容是 RGB"→"RGB 或深度"、"尺寸与节奏"、"✕ 不是第二个开关／不做拖动"→拆出"标题栏是拖动手柄"一条、"格子的 DOM"补名称顺序、"状态是视图态"补两格新态、"取证出口"改写读数与键面），§7.1 那条勾选框、§9.3 那条键各补一句，§12.33 的 **d**（`{320,240}` → `{256,192}`）与 **h**（"模式写死 rgb"）两支同轮换口径，§13.51 那一行在三处标注被撤销的点；新增验收 **§12.34**（四层，**本轮 ③ 真浏览器跑了**）与决议 **§13.52**。历史留在本卡，正文不写"曾经如何"。
- **本轮最重要的一处判断：借键，不 mint 键**。深度态的门用既有的 `viewport.cameraPreview.modes.depth`（Details 那两枚 tab 一直在用的那一枚）：窗里那枚 `<button data-camera-wall-mode="depth" data-feature="viewport.cameraPreview.modes.depth">深度</button>` 由 `applyFeatureVisibility()` 的既有循环**免费**门控，`logic.ts:cameraWallModeFor(features, requested)` 只是第二道（强点看不见的按钮也拿不到深度）。**为什么不叫 `viewport.cameraWall.depth`**：那会让"这台传感器能不能出深度图"同时有两枚键、两份真值，而远端只该有一个开关 —— 能力面（`viewport.cameraWall`）与态（`modes.depth`）各归各位。副产物：**键面纹丝不动**（88 键、CSV 89 行）⇒ **不需要重启 gateway**（**坑 22** 的前提这一轮不成立，这是本轮与卡 ㊺ 唯一的生效条件差别）。`cameraWallModeFor` 是**派生**不是**改写偏好**：入参不动、返回值动，`state.cameraWallMode` 仍是用户点的那一枚，键再打开时深度态自己回来。
- **第二处判断：伪彩是后处理，不是渲染器的第三种模式**。`renderSensorFrame(…, "depth", …)` 写进画布的仍是 §4.4 那张 `sensorDepth` 的灰度图，`main.ts:tintDepthFrame(canvas)` 在画完之后做一次查表（`getImageData` → `Uint32Array` 视图 → 取最低字节 → `logic.ts:depthPalette()` 那 256 项 → `putImageData`）。**代价写在 §4.8.9**：这条色带表达不了"没有测量" —— 打空的射线被清到 `far`、字节 `255`，与"真有一个东西在 `far` 上"同为最远端那个红；`NaN` 只在 `renderSensorDepth()` 那条 float32 米制通路里可表达，要区分就得改渲染器输出格式。**本轮不改，并把它测出来**（见下面的像素直方图）。**`renderer.ts` 与 `placement.ts` 一字未动** ⇒ "渲染器不读配置"那条分工（Q96/Q105）不需要新例外，Details 那格预览的灰度口径也不被这扇窗顺带改掉。
