## 任务卡原文

### FEAT-2026-10-23-A —— 阴影的开关分成两处：`viewport.shadows` 只藏勾选框，常量接手投影（Q118；新卡 ㉙；依赖 FEAT-2026-10-22-A）

- **起因（用户原话）**：「修改为 features.json 中的 viewport.shadows 控制浏览器是否显示勾选框，当 viewport.shadows 为 false 时，由 config/constant_config.json 中的 flag 决定是否投射阴影。当 viewport.shadows 为 true 时，由勾选框的状态决定是否投射阴影。」决议记 **§13.35（Q118，与 Q117 同表）**，正文**就地修订 §4.8.5 第 6 条与落点条**、**§7.1** 阴影那三条的第 1、3 条、**§9.2**（sample json +1 行、新增一条常量说明）、**§9.3** 的 Q117 那一段、**§12.19** 的 ① 与 ③，README 勾选框那段。触发点是上一轮收尾时的一次问答：用户在自己的 5173/8080 那套栈上看不到"投影阴影"勾选框，而 gateway 的 `features.json` 是**启动时快照**（坑 22），旧进程里根本没有这一键 ⇒ `featureEnabled` fail-closed ⇒ 宿主消失**且阴影一起不投**。一个键同时承担"控件给不给看"和"这条能力要不要"两种决定，在这种时刻是会误伤的，用户据此把两者拆开。
- **三条取舍**：**① 新键不进 `features.json`** —— `features.json` 的每一项都要能报出一个宿主（`parity_inventory.py` 判 `literal`/`gate_ancestor`），而这一条的宿主恰好是被 `viewport.shadows` 收走的那个控件；再放一个 feature 键就得到"两个键互相门控"的读法问题。**② 常量判据 fail-open 到 `true`** —— 与 §9.2 那两条数值键（Q97/Q101）同构，与本表历史上唯一的布尔常量 Q81（fail-closed）**相反**：Q81 门控的是一个会写现场的输入框，读不懂就该关；本键门控的是画不画影子，一条协议都不走（§4.8.5 第 1 条），读不懂最合理的解释是"没人配过"，那就该看到 §4.8.5 承诺的那个默认外观。**③ 常量那一路不冻结租约** —— 冻结的全部理由是"采集像素要可重复"，而启动配置天生在每个 tab 上重复；若在持锁期把 `shadows_enabled:false` 强制改成开，反而是把运维刻意的关闭偷换成渲染器的自作主张。**勾选框那一路冻结照旧**（Q117 那条判据不动）。
- **落点（判据收到一处纯函数）**：`logic.ts` —— `shadowsEnabled(features, runtime, checked, frozen)`（四元输入 → 一个布尔）+ `DEFAULT_SHADOWS_ENABLED`，与 `ghostOpacity()`/`waypointSettings()` 同族：吃 `Pick<RuntimeConfig, "shadows_enabled">`，`featureEnabled` 判键（**缺键仍是 fail-closed**，这一条不变），勾选那一路保留 `frozen || checked`。`main.ts` —— `renderShadows()` 不再自己相与，改为调用那条判据；`state.shadows` 的注释、`applyFeatureVisibility()` 里那句指向 `renderShadows` 的注释同步改口径；`toggleShadows()` 与 `renderLightingFreeze()` 一行不改（隐藏元素点不到，冻结分支只在可见那一路可达）。`renderer.ts` **零改动** —— 它本来就只收一个布尔，这正是 Q105/Q106/Q117 一贯的分工。**配置链四处**（坑 6）：`config/constant_config.json`、`local_gateway.py:DEFAULT_CONSTANT_CONFIG`、`contracts/types.ts` 与根 `types.ts` 的 `RuntimeConfig` 各加 `shadows_enabled`；gateway 的 `runtime_config()` 是 `{**self.config, "features": ...}` 整体透出，不需要新注册任何路由。
- **必须写进正文的实现细节**：**① `state.runtime` 在 `applyFeatureVisibility()` 之前赋值**（`start()` 里 `state.runtime = config; state.features = config.features; applyFeatureVisibility();`），所以第一次 `renderShadows()` 已经读得到常量；顺序反过来就会有一次"常量当默认值"的窗口。**② 键的 fail-closed 与常量的 fail-open 必须在同一个函数里**，否则下一轮改判据的人只看得见一半。**③ `tests/test_gateway_routes.py::test_default_config_file_matches_the_built_in_defaults` 是整表相等**，新键必须**两边同写**，不然这条既有红又多一处。**④ 冒烟要覆盖 `viewport.shadows:false` × 常量 `true`/`false` 两格**：只证 `page.route` 改 feature 键那一格，等于把 Q118 改判前那张错图又拍了一遍。
- **单测**：`logic.test.ts` 新增 `describe("shadow switching reads three sources (§4.8.5, Q118)")` **5 例** —— 勾选框那一路（常量为 `false` 也压不住勾选态，反向同理）、常量那一路（`state.shadows` 完全不参与）、冻结只钉勾选框那一路（`HIDDEN + false + frozen` 仍是 `false`）、六种读不懂的常量（缺字段/`null`/`"false"`/`0`/`1`/`NaN`）全回 `DEFAULT_SHADOWS_ENABLED`、**`viewport.shadows` 缺键时仍按 fail-closed 藏宿主但改问常量**（这条就是本轮的起因）。`renderer.test.ts` 那条"勾选框来回两次 `world.toJSON()` 全等"的负控制不动 —— 判据换了来源，渲染层性质一点没变。**全量 `npx vitest run` 466 例 / 16 文件**（本轮 +5）。python 侧在 `test_health_and_runtime_config` 里补一条 `assertIs(config["shadows_enabled"], True)`，钉住"常量确实随 `/api/runtimeConfig` 出门"。
