# 机器人仿真平台总体架构设计

## 1. 项目目标

本项目计划使用 C++ 开发一个模块化、可扩展的机器人仿真平台，并通过 Python SDK、Qt GUI、CLI 和通信接口向外部用户、算法模块及 Coding Agent 提供访问能力。

平台需要支持：

- 外部机器人与场景资产导入；
- 刚体与机器人动力学仿真；
- 场景碰撞检测与机器人状态碰撞查询；
- 实时或非实时仿真运行；
- RGB、深度、关节状态、雷达等传感器；
- Vulkan 图形渲染；
- C++ 与 Python 控制接口；
- Qt 图形化编辑和运行界面；
- 仿真状态保存、恢复、重置与回放；
- 可选的物理、碰撞、渲染及其他扩展后端；
- 外部算法模块、ROS 2、远程客户端和 Coding Agent 接入。

平台整体采用模块化设计。Physics Backend、Collision Backend、Render Backend 等服务均通过插件系统提供，可根据用户需要选择安装和加载。

# 3. 资源导入与资产处理系统

## 3.1 资源导入层

资源导入层负责读取外部资产，并将其解析为平台内部统一的 Asset IR。

第一阶段支持以下格式：

- URDF；
- OBJ；
- FBX。

后续可以扩展：

- USD；
- glTF；
- SDF；
- MJCF；
- Collada；
- STL；
- 其他机器人或三维场景格式。

主要依赖：

- `urdfdom`：解析 URDF；
- `Assimp`：解析 OBJ、FBX 等通用三维格式；
- 后续可以使用 `OpenUSD` 解析 USD。

资源导入层只负责读取和解析外部文件，不直接创建 Physics Backend、Collision Backend 或 Render Backend 中的对象。

各个后端不应直接解析 URDF、FBX、OBJ 或 USD。

------

## 3.2 Asset IR

Asset IR 是所有外部资产进入平台后的统一中间表示。

它用于消除不同资产格式之间的表达差异，并为后续验证、转换、烘焙和运行时场景创建提供统一输入。

Asset IR 可以包含：

```cpp
struct AssetIR {
    NodeHierarchy nodes;
    std::vector<MeshData> meshes;
    std::vector<MaterialData> materials;
    std::vector<TextureData> textures;

    std::vector<JointData> joints;
    std::vector<LinkData> links;
    std::vector<InertialData> inertials;

    std::vector<ColliderData> colliders;
    std::vector<SensorData> sensors;

    AssetMetadata metadata;
};
```

其中需要保留：

- 节点层级；
- 网格；
- 材质；
- 纹理；
- 机器人 Link；
- 关节；
- 惯性参数；
- 碰撞几何；
- 传感器定义；
- 原始资源路径；
- 坐标系和单位信息；
- 资源依赖关系。

------

## 3.3 资源验证与转换

资源转换阶段负责将 Asset IR 转换为平台使用的统一格式。

主要包括：

- 坐标系转换；
- 单位转换；
- 四元数格式转换；
- 网格索引标准化；
- 法线和切线生成；
- 材质参数标准化；
- 机器人关节树检查；
- 关节限位检查；
- 惯性矩阵检查；
- 碰撞几何生成；
- 碰撞网格简化；
- 凸包或凸分解处理；
- 纹理转换；
- GPU 资源准备；
- 后端专用资源生成。

平台不会修改用户的原始资产文件。

所有转换结果只存在于平台内部表示、运行时资源或 Baking Cache 中。

------

## 3.4 Baking Cache

为了避免每次启动仿真时重复解析和处理大型资源，平台增加 Baking Cache。

例如，用户通过 C++ 或 Python 指定：

```python
sim.load_scene("scene.usd")
```

平台仍然以原始文件作为场景初始状态来源，但可以优先检查缓存。

典型流程如下：

```text
读取资源路径
    │
    ▼
检查原文件及依赖文件是否发生变化
    │
    ├── 缓存有效 ──> 直接加载 Baking Cache
    │
    └── 缓存失效 ──> 重新解析、转换、烘焙并更新缓存
```

缓存有效性可以通过以下信息判断：

- 原始文件路径；
- 文件修改时间；
- 文件大小；
- 文件内容哈希；
- 依赖资源哈希；
- 导入器版本；
- Asset IR 版本；
- Baking 版本；
- 平台版本；
- 目标后端；
- 目标平台和 GPU 特性。

缓存内容可以包括：

- 已转换的网格数据；
- 碰撞网格；
- 凸包数据；
- 纹理压缩结果；
- Vulkan Buffer 所需数据；
- 材质中间数据；
- 机器人关节树；
- 运行时实体创建描述；
- 后端专用预处理数据。

Baking Cache 只用于加速加载，不改变以下语义：

> 每次新建仿真世界时，都从用户指定的原始资产所描述的初始状态开始。

如果原始资产发生变化，缓存必须自动失效。

------

## 3.5 USD 的定位

USD 在平台中被视为一种外部场景和资产格式，而不是平台运行时的权威场景表示。

其处理方式为：

```text
USD Stage
    │
    ▼
OpenUSD Importer
    │
    ▼
Asset IR
    │
    ▼
Runtime Scene
```

导入完成后，运行时场景与原始 USD Stage 解耦。

物理仿真产生的位置、速度和关节状态不会每帧写回原始 USD。

如果用户需要保存修改后的场景，应通过单独的导出模块完成，而不是直接修改原始资产。

第一阶段暂不实现 USD 导入，但相关接口应预留。

# 4. Runtime Scene 与 ECS

## 4.1 ECS 场景模型

平台内部采用 ECS，即 Entity-Component-System，作为统一运行时场景数据模型。

Entity 表示场景中的逻辑对象，例如：

- 机器人；
- Link；
- 刚体；
- 地面；
- 相机；
- 灯光；
- 雷达；
- 障碍物；
- 场景节点。

Entity 本身只包含唯一标识和基本元数据。

具体能力由 Component 组成。

典型组件包括：

```text
IdentityComponent
NameComponent
TransformComponent
HierarchyComponent
VisualComponent
MaterialComponent
ColliderComponent
RigidBodyComponent
ArticulationComponent
JointComponent
RobotComponent
ControllerComponent
SensorComponent
CameraComponent
LiDARComponent
LightComponent
SemanticComponent
BackendBindingComponent
```

不同系统只访问自己所需的组件。

例如：

- Physics System 访问 Transform、RigidBody、Collider、Joint；
- Collision System 访问 Transform 和 Collider；
- Render System 访问 Transform、Visual、Material、Light；
- Sensor System 访问 Sensor、Transform 及相关数据提供者；
- Robot System 访问 Robot、Joint、Controller、Actuator。

------

## 4.2 场景状态所有权

Runtime Scene 是平台逻辑状态的统一入口，但需要区分不同类型状态的权威来源。

例如：

- 名称、层级和语义信息由 Runtime Scene 管理；
- 动态刚体的实时位置和速度可以由 Physics Backend 产生；
- 渲染资源由 Render Backend 管理；
- 碰撞加速结构由 Collision Backend 管理；
- 传感器数据由 Sensor System 管理。

每次物理更新后，由同步模块将 Physics Backend 的结果同步到 Runtime Scene 的 Transform 和 Joint State 中。

禁止各个 Backend 互相直接修改对方内部状态。

------

## 4.3 场景层级与 Frame Tree

平台的坐标系和 Frame 设计尽量与 ROS 保持一致。

内部约定：

- 使用右手坐标系；
- X 轴向前；
- Y 轴向左；
- Z 轴向上；
- 长度单位为米；
- 时间单位为秒；
- 角度单位为弧度；
- 角速度单位为弧度每秒；
- 力单位为牛顿；
- 力矩单位为牛顿米。

相机光学坐标系参考 ROS 相机光学 Frame：

- Z 轴向前；
- X 轴向右；
- Y 轴向下。

平台需要提供统一的 Frame Tree，例如：

```text
world
└── robot_base
    ├── base_link
    ├── link_1
    ├── link_2
    └── camera_mount
        └── camera_optical_frame
```

API 应支持：

```cpp
Transform LookupTransform(
    FrameId source,
    FrameId target,
    SimulationTime timestamp);
```

所有传感器数据必须记录自身 Frame。

# 5. Sim Core

Sim Core 不实现具体物理、碰撞或渲染算法，而是负责整个仿真平台的组织、调度和状态管理。

Sim Core 拆分为以下内部模块。

------

## 5.1 World Manager

负责：

- 创建和销毁仿真世界；
- 加载和卸载场景；
- 管理 Entity；
- 管理 ECS Component；
- 管理场景层级；
- 管理多个 World；
- 管理默认 World；
- 管理场景重置。

平台未来可以允许同时存在多个隔离的仿真世界，以支持：

- 多环境强化学习；
- 批量规划；
- 自动化测试；
- 多场景对比；
- 并行仿真。

------

## 5.2 Simulation Scheduler

负责组织一次仿真 Step 中各个系统的执行顺序。

建议定义明确的仿真阶段：

```cpp
enum class SimulationPhase {
    PreUpdate,
    CommandUpdate,
    ControllerUpdate,
    PrePhysics,
    PhysicsStep,
    PostPhysics,
    CollisionSync,
    SensorUpdate,
    RenderSync,
    Render,
    EventDispatch,
    PostUpdate
};
```

一次典型的仿真更新流程为：

```text
1. 接收外部命令
2. 更新命令缓冲区
3. 更新机器人控制器
4. 更新执行器目标
5. 执行 Physics Pre-Step
6. 执行 Physics Step
7. 读取物理状态
8. 同步 Runtime Scene
9. 同步独立 Collision Backend
10. 更新传感器
11. 生成状态快照
12. 更新渲染场景
13. 执行渲染
14. 发布事件和观测数据
```

调度器需要支持：

- 固定顺序；
- 系统依赖关系；
- 多频率系统；
- 同步执行；
- 后续扩展异步任务；
- Headless 模式；
- 暂停；
- 单步执行；
- 快进；
- 实时节奏控制。

------

## 5.3 Time Manager

平台区分以下时间：

- Simulation Time：仿真时间；
- Wall Time：现实时间；
- Physics Time：物理步时间；
- Control Time：控制器更新时间；
- Sensor Time：传感器采样时间；
- Render Time：渲染时间。

核心物理仿真使用固定时间步长。

例如：

```text
Physics：500 Hz，dt = 0.002 s
Controller：100 Hz，dt = 0.01 s
Camera：30 Hz
LiDAR：10 Hz
GUI：60 Hz
```

用户可以配置：

```cpp
simulation.SetPhysicsTimeStep(0.002);
simulation.SetRealTimeFactor(1.0);
```

Real-Time Factor 表示仿真时间与现实时间的目标比例：

- `0.0`：不限制速度，尽可能快运行；
- `0.5`：半实时；
- `1.0`：实时；
- `2.0`：两倍实时。

实时模式不会将不稳定的 Wall Time Delta 直接交给物理引擎。

物理引擎仍然使用固定步长，Time Manager 只负责控制执行节奏。

------

## 5.4 Command System

所有外部操作首先转换为 Command，再由 Sim Core 在明确的仿真阶段执行。

典型命令包括：

```text
CreateEntityCommand
DestroyEntityCommand
LoadSceneCommand
ResetWorldCommand
SetTransformCommand
SetJointPositionCommand
SetJointTargetCommand
ApplyForceCommand
CreateSensorCommand
StartSimulationCommand
PauseSimulationCommand
SaveStateCommand
RestoreStateCommand
```

这样可以避免 Python、GUI、RPC 和 Agent 直接修改正在运行的 ECS 或 Backend 状态。

命令可以包含：

- 提交时间；
- 目标执行时间；
- 命令来源；
- World ID；
- Entity ID；
- 权限信息；
- 执行结果。

------

## 5.5 Event System

Event System 负责发布仿真内部事件。

典型事件包括：

```text
EntityCreated
EntityDestroyed
SceneLoaded
SimulationStarted
SimulationPaused
SimulationReset
CollisionStarted
CollisionPersisted
CollisionEnded
JointLimitReached
SensorFrameReady
BackendError

```

事件可供以下模块订阅：

- GUI；
- Python SDK；
- 日志系统；
- 调试工具；

- 状态录制系统。

## 5.8 Backend Manager

Backend Manager 负责：

- 根据用户配置选择 Backend；
- 创建 Backend 实例；
- 检查 Backend 能力；
- 检查 Backend 组合是否有效；
- 管理 Backend 生命周期；
- 组织 Backend 状态同步；
- 处理 Backend 异常；
- 向 Sim Core 提供统一接口。

用户可以选择以下三种碰撞和物理组合模式：

### 模式 A：物理引擎同时提供动力学和碰撞查询

```text
Physics Backend: MuJoCo
Collision Query: MuJoCo
```

适用于常规仿真。

### 模式 B：物理引擎与独立碰撞后端同时存在

```text
Physics Backend: MuJoCo
Collision Backend: FCL
```

适用于：

- 路径规划；
- 临时机器人状态碰撞查询；
- 多线程碰撞查询；
- 使用不同碰撞近似模型；
- 不希望修改主物理世界状态的查询。

### 模式 C：只加载碰撞后端

```text
Physics Backend: None
Collision Backend: FCL
```

适用于：

- 离线路径规划；
- 静态场景分析；
- 批量配置碰撞检查；
- 无需动力学的机器人算法。

------

状态内容至少包括：

- 仿真时间；

- Transform；
- 刚体速度；
- 关节位置；

- 执行器状态；

```cpp

```

## 5.10 Snapshot 与状态同步

为了避免渲染、传感器、GUI 和通信模块直接读取正在被物理系统修改的数据，平台引入状态快照。

```cpp
struct WorldSnapshot {
    SimulationTime timestamp;
    uint64_t sequence;

    std::vector<EntityTransform> transforms;
    std::vector<JointState> joint_states;
    std::vector<RigidBodyState> rigid_body_states;
};
```

第一阶段可以使用同步流程：

```text
Physics Step
    ↓
更新 Runtime Scene
    ↓
生成 Snapshot
    ↓
Render 和 Sensor 读取 Snapshot
```

后续可以扩展为：

```text
Physics 生成 Snapshot N+1
Render 使用 Snapshot N
```

并通过插值降低视觉延迟。

渲染与物理是否并行应当是运行策略，不应固化在接口中。

# 6. Robot and Control System

Robot System 用于统一管理机器人模型、关节、运动学、控制器和执行器。

主要模块包括：

```text
Robot Model
Kinematics
Joint State
Controller
Actuator
Command Buffer
```

```cpp
if (!physics->GetCapabilities().rigid_body_dynamics) {
```

# 8. Collision Backend

Collision Backend 用于几何碰撞检测和空间查询。

碰撞查询分为以下类型。

------

## 8.1 场景碰撞查询

```cpp
CheckCollision(entity_a, entity_b);
CheckSceneCollision(entity);
CheckSelfCollision(robot);
GetContactPairs();
```

------

## 8.2 空间查询

```cpp
Raycast(ray);
RaycastBatch(rays);
ShapeCast(shape, start, direction);
Overlap(shape, pose);
Distance(entity_a, entity_b);
ClosestPoints(entity_a, entity_b);
```

------

## 8.3 机器人状态碰撞查询

路径规划器通常需要在不修改主仿真世界的情况下检查大量候选关节状态。

因此需要提供独立 Collision Query Context。

```cpp
auto context = collision_backend.CreateQueryContext();

context.SetRobotConfiguration(robot, q);
bool result = context.CheckCollision(robot);
```

还可以支持：

```cpp
CheckConfiguration(robot, q);
CheckTrajectory(robot, trajectory);
CheckConfigurationsBatch(robot, q_batch);
```

Query Context 可以拥有独立的临时 Transform 状态和碰撞加速结构。

这样 OMPL、TrajOpt 或其他规划算法可以进行并发查询，而不会修改主 ECS 或 MuJoCo 世界中的机器人状态。

## 8.4 第一阶段碰撞实现

第一阶段支持：

### MuJoCo Collision Query

优先复用 MuJoCo 内部碰撞能力，适合正在运行的物理世界。

### FCL Collision Backend

作为独立碰撞后端，主要用于：

- 路径规划；
- 机器人临时状态检查；
- 距离查询；
- 自碰撞检查；
- 静态场景碰撞检查。

# 9. Backend 组合校验

用户可以自行选择 Physics、Collision 和 Render Backend，但平台必须在启动前验证配置。

例如：

```yaml
physics_backend: mujoco
collision_backend: fcl
render_backend: vulkan
```

Backend Manager 应完成以下检查：

- 插件是否存在；
- 插件版本是否兼容；
- 目标操作系统是否支持；
- 硬件是否支持；
- Backend 是否具备所需能力；
- Backend 组合是否允许；
- 运行模式是否与能力一致；
- 所需资源是否可以被转换；
- 状态同步路径是否存在。

错误配置示例：

```yaml
physics_backend: fcl
```

FCL 不提供动力学，因此如果用户要求运行物理仿真，平台必须拒绝启动，而不是静默降级。

错误信息示例：

```text
Backend configuration error:

Selected physics backend "FCL" does not provide rigid-body dynamics.

Required capability:
    rigid_body_dynamics = true

Available capabilities:
    collision_query = true
    distance_query = true

Suggested configurations:
    physics_backend = mujoco
    collision_backend = fcl
```

对于非关键能力缺失，可以警告并降级。

例如 Backend 不支持确定性状态恢复时：

```text
Warning:
The selected physics backend does not guarantee deterministic replay.
State restore is available, but replay results may differ.
```

能力校验分为：

- Fatal Error：无法继续，直接退出当前 World 创建；
- Warning：可以继续，但部分功能不可用；
- Information：启用替代路径或性能较低的实现。

# 21. 第一阶段完成标准

第一阶段可以定义以下验收场景：

1. 通过 Python SDK 加载一个 URDF 机器人；
2. 通过 FBX 或 OBJ 加载桌面和障碍物；
3. 将场景转换为 ECS Runtime Scene；
4. 使用 MuJoCo 创建机器人动力学世界；
5. 使用 MuJoCo 或 FCL 执行碰撞检查；
6. 使用 Vulkan 渲染场景；
7. 在 Qt GUI 中查看机器人和场景；
8. 通过 Python 发送关节位置目标；
9. 运行固定时间步仿真；
10. 获取 RGB、Depth、Joint State 和 LiDAR 数据；
11. 保存当前仿真状态；
12. 继续运行若干步；
13. 恢复之前的状态；
14. 验证机器人状态和仿真时间正确恢复；
15. 通过 Agent RPC 创建一个简单障碍物并修改其位置；
16. GUI 自动显示 Agent 对场景的修改；
17. 对错误 Backend 组合给出明确错误并拒绝启动；
18. 第二次加载相同资源时命中 Baking Cache，并显著降低加载时间。

满足以上内容后，平台即可形成第一条完整闭环：

```text
外部资产
    ↓
Asset IR 与 Baking Cache
    ↓
ECS Runtime Scene
    ↓
MuJoCo Physics
    ↓
MuJoCo / FCL Collision
    ↓
Vulkan Render
    ↓
RGB / Depth / Joint State / LiDAR
    ↓
C++ API / Python SDK / Qt GUI / Agent RPC
    ↓
状态保存、恢复与自动化测试
```
